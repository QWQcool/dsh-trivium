# 0.7.0 前端与产品设计查验

日期：2026-10-28。对象：0.7.0 发布源码及本轮未发布工作树。相关入口：[当前基线](README.md)、[缺陷查验](bug-audit-2026-10-28.md)、[同类插件与路线](memory-plugin-landscape-2026-10-28.md)。

## 1. 本轮确实做了什么

- 阅读 `lib/client.js`、设置 API、存储与抽取调用路径；审查实际请求的工作区绑定和异步完成顺序。
- 新增 `scripts/smoke-p24.mjs`：通过宿主注册接口取得真实 bundle 的 Settings 组件，用受控 React hooks/fetch 调度执行组件。它不加载真实 DOM，不代替浏览器布局或焦点验收。
- 五项原始行为回归在修改前全部失败、修改后通过；独立复核又补出“写操作完成后用旧筛选刷新”的第六项，先失败再修复。最终 P24 为 6/6。
- 实际打开本机 DeepSeek Harness 桌面客户端；可执行文件版本 `0.2.1-rc.3`，插件面板显示 `0.7.0`，窗口约 1280×820，浅色主题。
- 只查看现有工作区和只读界面，不提交节点编辑、归档、删除、导入，不发送模型消息。破坏性与并发测试使用合成数据、受控请求或临时库。
- 桌面宿主观察到了工作树前端热更新：条目标题从普通文本组变为原生按钮。本轮不是从独立安装的最终发布包执行完整桌面验收。

## 2. 已修复的前端缺陷

| 级别 | 触发与原行为 | 本轮修复 | 证据 |
|---|---|---|---|
| P1 | 面板显示工作区 A，另一会话使服务器 `activeCwd` 变成 B；A 的节点操作不带 cwd，同号节点可能写到 B | 面板绑定首次显示的工作区；列表、外部文件发现、刷新、节点写入、合并、导入导出、向量回填、旁路生成显式带 cwd | P24 工作区请求断言；服务端无 cwd 时使用全局 activeCwd 的代码路径 |
| P2 | 快速改变搜索条件，旧列表响应或旧错误晚到，覆盖新结果 | 每个异步加载阶段和异常出口都校验请求序号 | P24 人为颠倒响应完成顺序 |
| P2 | 归档等 POST 尚未完成时用户改了搜索；POST 完成后旧闭包调用 load，用旧条件覆盖新列表 | load 从当前筛选 ref 读取参数，写后刷新保留用户最新筛选 | 独立评审追加的第六项红→绿回归 |
| P2 | 条目标题是带 onClick 的 div，鼠标能展开，Tab/Enter 不能正常操作 | 改为原生 button，提供 `aria-expanded`，保留原有视觉样式 | P24 控件语义；桌面实际 Tab→Enter 展开 |
| P2 | 设置列表永久删除直接发送请求；芯片入口却有确认，两个入口保护不一致 | 复用现有删除说明；取消时不发写请求 | P24 取消删除无请求；没有在真实库中试删 |
| 文案 | README 无条件宣称抽取在本机、对话不外发 | 中英文 README 与抽取说明区分本地存储、宿主模型调用、可选远程 embedding | `makeLlmCall` → `ctx.llm.stream` 与 `distill` 的实际调用链 |

旁路“删除 jsonl”仍是针对所有已知工作区的既有操作，当前文案也明确写了范围；不能把它当作单库接口随手改掉。后续可讨论改成显式列出目标的维护操作。

## 3. 桌面视觉／键盘具体指什么

视觉检查关注内容能否看清和完成操作：标题、正文、按钮是否挤压；长路径是否换行；滚动是否能到达所有区域；浅深色错误和禁用状态是否可辨认；弹窗是否遮挡关键内容。

键盘检查关注没有鼠标能否完成同一流程：Tab/Shift+Tab 到达控件，焦点有明确边框；Enter/Space 激活；弹窗不会让焦点跑到背景；Escape 逐层关闭；关闭后返回合理的触发控件。

| 本轮动作 | 实际观察 | 不能据此声称 |
|---|---|---|
| 打开 Settings → Trivium 记忆 | 标题、配置折叠、记忆列表、召回检查均正常显示，没有空白或崩溃 | 不代表所有宽度、所有数据规模都正常 |
| 召回检查按 Tab | 查询输入框→运行只读检查→检查版本链；有可见焦点，底部按钮会随焦点滚入视口 | 未完成所有控件、嵌套替代弹窗的闭环 |
| 修复后从列表筛选按 Tab | 首条记忆标题可获得蓝色焦点框 | 不等于所有屏幕阅读器均验证通过 |
| 标题按 Enter | 展开内容／来源／决策历史页签，未写入数据 | 未验证所有详情错误与冲突状态 |
| Escape | 外层设置弹窗关闭 | UI Automation 只报告 RootWebArea，未能确认焦点回到原触发器或输入框；不能沿用旧报告“已归还输入框”的结论 |

尚未在本轮完成：900px 临界宽度、深色主题、嵌套替代弹窗焦点圈、两个独立浏览器进程的 409、真实宿主 UI 的导入故障恢复、最终 tarball 的桌面全流程。390px 仍是明确范围外。

## 4. 目前界面表现与改进顺序

整体是可工作的管理面板，尚未形成很清楚的日常操作顺序。它与宿主的浅色风格一致，配置默认折叠、列表与召回检查分开是合理选择；但“检查更新”和维护说明占据首屏，常用的记忆操作被推到下方。

| 观察 | 影响 | 建议 |
|---|---|---|
| 首屏先是版本检查、配置，再是条目 | 打开面板后要先经过低频管理信息 | 默认首先展示当前工作区与记忆搜索；更新放到次级“关于／维护”区 |
| 提示文字多为 11–12px、低透明度，混用 until/L0/autoRecall/compaction | 技术用户能理解，但阅读费力，非技术用户难判状态 | 正文至少按宿主正常字号；主要标签用“有效期／摘要／自动召回／会话压缩”，技术标识放详情 |
| 保存设置按钮常驻，部分开关立即保存、部分输入还需手动保存 | 不容易知道是否已经生效 | 即时保存项统一就地回执；需要提交的表单独立显示未保存状态，不把两者混成一个动作 |
| 已过期、已替代、已归档、脏数据来自不同维度 | 连在标题上时像一串诊断文本 | 主状态只保留“当前／历史／已归档”，期限和来源质量做次级标签；不要改变底层语义 |
| 列表每行直接摆归档、删除、替代等动作 | 密度高，危险动作与常用操作同级 | 正文/详情为主操作；永久删除进入更多菜单，保持确认和明确对象 |
| “召回检查”同时放预览、投递、更正、完整性体检 | 用户不容易区分模拟结果与已发送事实 | 分为“这一轮实际发送”“试算一次查询”“维护检查”；复用现有页签，不新增一套工作台 |
| tablist 只有 role/selected，没有完整方向键/roving-tabindex 约定 | 当前主要依靠逐个 Tab | 与宿主 tab primitive 对齐；嵌套弹窗复用宿主对话框 primitive，单独验焦点圈 |
| 芯片和设置重复提供新增/归档/删除 | 两处都合理，但容易出现反馈与确认不一致 | 共用请求与结果处理；让芯片负责“这一轮用哪些”，设置负责“库里存什么” |

这些是下一批 UX 范围建议。本轮修复明确缺陷并纠正文案，没有重排整页、引入新 UI 框架或改变默认开关。

## 5. 设计合理性与冗余判断

| 设计 | 判断 | 后续处理 |
|---|---|---|
| 四工具、find→read、少注入 | 合理：将检索与全文读取分开，控制接口规模 | 先提高回执和可解释性，不加第五工具 |
| URI 身份、事务、ETag、操作幂等、预算账本 | 必要复杂度：对应身份丢失、半提交、过期覆盖和重复投递 | 保留；用真实运行时回归维护，不能为“简洁”删除保护 |
| JSON 与 JSONL 的两套导入实现 | 实现冗余且曾产生行为分叉 | 本轮已合并事实校验/提交；保留 JSON 合并与 JSONL 快照同步的差异 |
| 自动召回、预览、主动工具 | 用户意图不同，不能直接合为同一产品行为 | 共用版本投影和基础过滤，分别保留预算与历史读取规则 |
| `.tdb*`、JSON、JSONL、Markdown | 各有用途，但文档曾混淆主库、交换和备份 | 给出统一恢复说明；不承诺 JSONL 含向量/会话/pins 或可代替完整备份 |
| 芯片下的会话画布 | 与“记忆核”主目标关联较弱，维护成本偏高 | 继续默认关；先做宿主兼容，暂缓扩成功能工作台，是否拆包由使用数据决定 |
| 更正队列进程内、pins 优先、依赖注入开关 | 合理取舍仍有缺口：重启丢诊断，pins 占满可使更正长期等待，关闭注入可能不送更正 | 需要明确送达契约与状态说明，再选择预留预算或优先级；本轮不静默改变默认行为 |
| 巨型客户端 bundle、历史兼容路径 | 有维护压力，但宿主 loader 限制相对 require | 先提取可测试的逻辑边界和行为测试；正式建立 bundle 构建后再拆分源文件，不只做形式重构 |
| 自动抽取默认开 | 易用性有利，但“本地记忆”容易让用户误判联网和费用 | 已修准确说明；后续可讨论规则-only模式，而不是将现有模型抽取冒充离线 |
| 首次面板选库与全局诊断 | 首次仍从服务器 activeCwd 取库；部分 lastExtract/lastPlan/sidecarHealth 仍是全局状态 | 本轮固定的是面板已显示的库，不能宣称必然等于前台对话的库。后续提供显式工作区选择并将健康/诊断按库归属，避免把另一库成功当成本库成功 |

下一步优先把“写入是否成功、这一轮到底发了什么、为什么没发、如何恢复”解释清楚，再基于固定评测改召回。长期特色应延伸为可更正、可溯源的决策图，以及失败→修复经验路径。
