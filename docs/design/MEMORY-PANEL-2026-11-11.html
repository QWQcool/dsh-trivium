    建议开工顺序

    0.8.8 先交付已有写入修复和准确的操作反馈。

    1. 先绑定操作所属的工作区

      F88-01　提案读回时记住它属于哪个库。切库立即清空提案和待补写缓存，丢弃旧请求的迟到结果。点击确认或保持时再次核对工作区和提案版本。用两座节点 ID 和 ETag 相同的库验收。

    2. 补齐两个操作结果

      A1　保持原样后写一条独立审计记录，保留候选 ID。动作完成但审计写入失败时，在面板显示警告。A2　外部导入失败时读取部分提交回执，刷新库计数，给出同一来源的重试提示。

    3. 冻结修复范围，复核写路径

      复用 p89 验证提案与锁，复用 p83 验证外部导入。将第二进程持锁的面板写路由纳入发前复核，检查拒写时内容完整、释放后可重试。前端视觉细化单独排期。

    4. 获准后准备并发布 0.8.8

      A3　取得 bump 授权后同步包、锁文件和四处版本声明，写双语发布说明。冻结提交，跑 p91、全量回归与证据校验，核对实际 tgz 的清单和哈希。独立安装该 tgz，在隔离 DSH 宿主人工走查切库、拒绝和导入失败。A4　经明确授权发布同一产物，核对 registry、冻结提交的 tag 和 GitHub Release。

    5. 发后做导入基准和界面细化

      先比较真实外部导入的新增与重导，记录 p50/p95、有效写入数、flush 次数和重开后的内容。界面优先做候选正文对照、待处理事项前置、搜索和筛选分层。脚本现为 118/120，已有脚本可以承接这些契约回归。

    评审与复核记录

    产品事实、设计取舍和验收方法均以 2026-11-11 的基线为准。

    切换工作区的提案为什么应当先修

    切换时面板立即更新当前工作区，清理函数遗漏了提案。提案请求回来时直接更新列表。提交时面板又从当前选择生成请求地址。ETag 对节点和候选的内容作校验，其中没有工作区标识。面板读取与提交 · 提案版本计算

    两个临时库有编号、名称和正文相同，原句不同的提案。用既有 p26 组件夹具加载真实面板代码，延迟 A 的列表，切至 B 并显示 B 的列表，再交付迟到的 A 响应。工作区选择器仍是 B，卡片却显示 A 的原句。点击“保持原样”，把组件实际产生的请求转交回环 HTTP 路由，返回 200。A 仍有 1 条待确认，B 从 1 条变成 0 条。修复后在相同顺序下，旧行应失效。最后在隔离宿主手工复核。

    界面细节如何映射到现有能力
    • 记忆库　窄栏里将搜索放在第一行，类型、过期和已替代收入筛选。条目先展示名称和正文，在展开详情后提供编辑、归档和删除，沿用已有删除确认。
    • 运行记录　当前先显示诊断和待补写，再显示提案。候选接口已经给出最多 160 字正文，列表只展示编号和名称。稿件用正文区分同名候选，确认只作用于选中的目标，保持原样作用于整条提案。
    • 上下文　已送达的账本与只读试算各有入口。试算完成后保留本轮实际发送的原文，让人能分清“已经发送”和“会选什么”。
    • 设置　把导入回执放在触发操作的来源旁。后续把“保存向量连接”放到地址、模型和凭据输入旁，用已有设置接口，清楚标识显式保存与即时生效的选项。
    • 视觉　沿用宿主明暗和青绿色，将强调色留给当前页与确认动作。琥珀色表示需要查看的部分提交。状态同时有文字，原句与诊断可展开。新版计划只需替代已过时的待办。既有四页与窄栏走查 · 原宿主记忆库截图
    A1 与 A2 的实现和验收边界

    A1 当前成功拒绝已保存墓碑、候选和时间。沿用现有变更日志给人工拒绝一个独立的双语原因码，成功一次记一行。陈旧 ETag、重试和持锁 409 不应多记一行。确认路由现以必填 ETag 推断“来自面板”，只能据此证明来自 HTTP 接口。两条路由均应如实标注来源、保留写入警告，面板要读取成功响应中的警告。HTTP 路由 · 变更原因和双语标签

    A2 当前的 api() 只在异常上留下状态、错误码和消息，有 HTTP 状态的失败一律显示为“被拒绝”。只对外部导入的 partial === true 采用部分提交措辞。newNodesBeforeFailure 是观测到的节点净增量，0 仍可能有合并，null 表示未知。合并、跳过和剩余总数都不能由它推出。按 retryHint 告知如何补齐。现有按钮会重新发现全部来源，若要给出稿中的“一键重试”，需锁定原来源集合并通过 ids 重发。0.8.8 可先只显示提示。通用 JSON 导入已有预检、指纹和事务，旁路更新失败另有反馈。外部导入回执 · 落盘与重试契约
