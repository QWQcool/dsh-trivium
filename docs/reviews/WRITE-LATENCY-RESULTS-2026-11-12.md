# 5000 节点写入延迟归因与插件侧优化

2026-11-12。基线为已发布 0.8.9 后的 main@daac859。Node 24.15.0，triviumdb 0.9.0，Windows x64 原生二进制 SHA-256 为 b5a7d6f30820d2a4b91aa8a18d5b63ebccd3f07baeae7f87883bb4fa9f74f9ab。模型调用 0 次，费用 ¥0。

## 原来的 288ms → 807ms 怎样解释

原报告基线只有 3 次写入，带查询只有 15 次，nearest-rank p95 均等于各组最大值，不能作为稳定的查询增量成本。逐请求核对如下。[原始 0.8.9 数据](evidence-0.8.9/live-tql-bench.json)

| 同一次慢写入的边界 | 耗时 |
|---|---|
| 客户端往返 | 806.535ms |
| HTTP 处理器 | 805.103ms |
| 原生 flush | 801.447ms，占客户端往返约 99.4% |
| 处理器内除 flush 的部分 | 3.656ms |
| 客户端与处理器的其余差额 | 1.432ms |
| 同轮已完成的查询原生调用 | 2.252ms，独立于该次写入计时 |

同时的状态请求往返为 807.511ms，处理器本身只用 1.331ms。其余主要表现为等待同步 flush 结束后才能处理请求。这个等待不能再加成一笔独立的查询计算成本。

## 对照方法

使用真实 registerMemoryApi、独立宿主进程和独立 HTTP 客户端。临时库固定 5000 节点、1536 维、17 个 hub、10981 条业务边。embedding 和 Git 旁路在实验设置中关闭。先做 5 组写入/查询预热，再轮换执行每个控制各 30 次，避免基线始终先跑。最后执行 30 批、每批 8 条归档。重复归档同一组 ID，每次仍会更新其时间戳。

两份源码使用同一个测量程序。旧库代码由 daac859 提取，依赖链接到同一套安装。原生调用分别记录 flush、查询、索引喂入、payload 读取及 CPU 时间。高频调用只累计计数和耗时，跨进程使用相同的 OS 单调时钟。窗口 GC 单独记录，不把重叠时间重复相加。

```powershell
# 从旧源码副本运行相同 benchmark
node <baseline>/scripts/bench-live-tql.mjs --sizes 5000 --scenario attribution --reps 30 --query-timeout-ms 50 --hard-timeout-ms 300000
# 当前优化源码
node scripts/bench-live-tql.mjs --sizes 5000 --scenario attribution --reps 30 --query-timeout-ms 50 --hard-timeout-ms 300000
```

建立旧源码副本时可运行 git archive daac859，仅提取 lib、scripts 和 package.json，将当前 benchmark 复制到副本的 scripts，并链接同一 node_modules。性能测量期间没有并行运行回归测试。前后为独立进程、独立库、先后两轮，不能排除系统存储负载差异。源码指纹和每次请求的完整计时均保留。[优化前记录](evidence-write-latency-2026-11-12/before.json) · [优化后记录](evidence-write-latency-2026-11-12/after.json) · [计算结果](evidence-write-latency-2026-11-12/comparison.json)

计时记录保留全部数值、原生 trace 和检查，附原始输出 SHA-256。旧输出中通用负载模式的说明已用本节的归因模式元数据替代，数值没有调整。每轮 **306/306** 检查通过。

## 查询、flush 与调度

| 控制路径，各 30 次 | 优化前 p50 / p95 | 优化后 p50 / p95 |
|---|---|---|
| 仅普通编辑 | 179.348 / 224.049ms | 115.117 / 673.078ms |
| 同时发送短查询与编辑 | 184.708 / 237.564ms | 116.863 / 596.160ms |
| 查询完成后再编辑 | 193.464 / 1047.449ms | 114.308 / 220.896ms |
| 仅短查询 | 2.843 / 4.146ms | 1.938 / 2.265ms |
| 绕过插件处理，直接改 payload 后 flush | 182.036 / 598.724ms | 113.743 / 453.068ms |
| 无新增业务修改，直接 flush | 170.851 / 622.958ms | 113.410 / 700.059ms |

单次编辑路径没有被这次补丁优化，p95 仍会随 flush 尖峰波动。不能把两轮里的普通编辑差异宣称为收益。即使没有查询、没有插件写入处理，flush 控制也出现了长等待。

带短查询的编辑，其到达处理器前的等待/传输 p95 为 3.728ms、2.239ms，处理器里其余工作 p95 为 4.197ms、2.132ms。慢写入对应的长时间仍落在 flush 区间。各阶段的 p95 来自各自分布，不能直接相加。

## Windows 线程和 I/O 补充采样

另建 5000 节点、1536 维的原生控制库，仅含工作区归属边，交替执行有 payload 修改和无业务修改的 flush，共 40 次。使用系统 GetProcessIoCounters 和 .NET 主线程状态读取，目标采样休眠为 20ms，实际中位间隔 45.867ms。[采样结果](evidence-write-latency-2026-11-12/windows-io.json)

采样窗口内累计写入约 **1.412GB**、读取约 **3.943GB**，平均每次约 35.3MB 写入。无业务修改的第 25 次 flush 用时 **870.741ms**，CPU **172ms**，窗口内观察到约 **35.3MB** 写入。该调用内 21 个采样点中有 17 个为 Executive 等待，4 个 Running。

字节口径是该进程的 I/O 记账，物理设备流量仍需另测。[GetProcessIoCounters 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters)

这将主要成本定位到原生持久化过程的大文件组 I/O 与等待。它没有表现为单纯的 JS 查询计算或 JS 回调调度成本。Executive 等待不能进一步区分文件同步、原生锁或其他系统等待，采样也不能证明每一个空窗的原因。**F-LAT-01 仍开放**，单次 flush 的具体内部等待类型需要更细的原生/OS trace。

## 已实施的低成本改动

1. **归档取消重复全文索引重建。** 归档只改 status 与 updatedAt，indexTextFor 的输入字段没有变化。保留原生 status 索引更新与现有搜索可见性规则，避免每条归档重新读取、喂入全部 5000 条文本。
2. **芯片批量写共用一次 flush。** 使用已有同步 runDeferredWrites，最终 flush 成功后再返回。若后续操作失败，finally 先保存此前已完成的写入，再报告错误。空、缺失及全被版本链保护的批次没有新增 flush。
3. **芯片列表只取 payload。** 该响应只用 payload 字段，改用 getPayload，避免逐条搬运整节点中的向量和关系对象，保持返回结构。

| 每批归档 8 条，共 30 批 | 优化前 | 优化后 |
|---|---|---|
| 客户端 p50 | 5382.507ms | 161.812ms，下降约 97.0% |
| 客户端 p95 | 8064.765ms | 946.439ms，下降约 88.3% |
| 全部批次 flush 次数 | 240，每批 8 次 | 30，每批 1 次 |
| 全文索引文本喂入次数 | 1,200,000，每批 40,000 次 | 0 |
| 批次 flush 总时间的 p95 | 2831.243ms | 904.484ms |
| 索引喂入/读取时间的 p95 | 4841.310ms | 14.677ms |
| 其余处理时间的 p95 | 939.945ms | 22.844ms |

这些收益限定为本机这套批量归档负载。优化后的 p95 中，flush 仍占主要部分。删除批次也合并 flush，但保留原有的删除后全文索引重建，不能套用归档的收益比例。

首批 8 条此前均未归档，实测为 8731.232ms → 151.022ms。它支持首次操作也能减少重复工作，单批数据不构成延迟保证。
