## 二、A：授权决策走 P（替代 0.8.6 的 C）

### 2.1 行为

| 场景 | 0.8.6（C） | 0.8.7（P） |
|---|---|---|
| 用户说"别用方案 A，改用方案 B" | 立即建 `supersedes` 硬边，A 退出短地图 | 写入 B，标 `review:"supersede-proposed"` + `proposedSupersedes:[A]`；**A 仍是 head，两条都在短地图** |
| 标签有歧义（两条都叫"方案 A"） | 只标 `ambiguous-supersede`，无候选列表 | 提案带上**全部候选 id**，由人挑一个 |
| 模型声称替代 | C 里仍可能误退休 | 模型只能提案；没有"模型直接确认"的通道 |
| 确认 | 无此步骤 | `POST /nodes/<A>/supersede {successorId: B}`（复用既有修订接口）+ 清标记 |
| 拒绝 | 无此步骤 | `POST /supersede-proposals/<B>/reject`，两条都保持现行 |
| 列表 | 无 | `GET /supersede-proposals` |

设置开关：`~/.dsh/trivium.json` 的 `supersedeMode`，**缺键 = propose**；`"auto"` 恢复 0.8.6 行为（仅作逃生口，面板不暴露）。

### 2.2 为什么短地图不能隐藏提案节点

`lib/store.js` 原本对任何带 `review` 的节点直接跳过（那是给"歧义替代"用的，避免两个互相矛盾的当前值）。P 下如果沿用，**用户刚说的新决策会从地图里消失**，模型只会照着旧值回答——比 C 更糟。所以改成只跳过"非提案"的 review 标记。

准确的说法是**两条都保持现行、都有入选资格**，不是"两条都一定显示"：短地图有 8 个命名槽位和 token 预算，夹具小的时候两条都在，库大时可能只有一条被展开。这个措辞已在报告与面板文案里改掉（复审 P2）。

### 2.3 **有意偏离**：不给模型 `supersedes_id`（**请复审重点看**）

`SUPERSEDE-CONTRACT-OPTIONS.md` 写的是"硬链接只由**用户在面板确认**或**调用方用结构化参数给出目标 id**创建"。实现按"**模型工具不提供确认能力**"这一条收口，但**不宣称这是权限隔离**——"人写的调用代码"同样不是身份认证：

- 面板 → 提案确认接口（人点头，仍需带 ETag）；
- 外部集成 → 同一个接口（调用方是人写的代码，不是模型）；
- **模型没有任何确认路径**：不给 `supersedes_id`，也不给"确认"动作。0.8.6 里曾经加过 `supersedes_id`，后来撤掉了。

理由：四轮复审的攻击案例里，"模型给出显式 `supersedes` 字段"正是误退休的载体（"带该字段时同样误退休"）。给模型一个 id 参数等于把 P 刚关上的洞重新打开，只是换了字段名。**代价**：模型只能提案。8 个候选里要挑哪个，本来也只有人能决定。

### 2.4 存量数据（A7）

0.8.6 用户库里已经由 C 自动建出的 `supersedes` 边**保持原样，不回滚、不改写**。理由：无法可靠区分"当时用户真的改口"与"误退休"，自动降级会把正确替代也打回未确认，造成召回倒退。文档写明"0.8.7 之前建立的替代边来自旧契约"，新契约只对新增生效。**如果复审认为应当统一降级，这是一条独立迁移任务。**

### 2.5 面板

「运行记录」页新增"待确认替代"卡片（`data-page-card="proposals"`）：每条列出提案正文、原句、每个候选一行，**逐候选"确认替代"按钮**，以及"保持原样"。不提供"一键全部确认"——挑目标正是这一步要人做的判断。

按 `AGENTS.md` §5 **没有新增 UI 断言**；只做了 `node --check`、设置页回归（p78 56/56）与 p18 的 wiring 断言更新。这条卡片**没有渲染层测试**，请复审时人工看一次。

### 2.6 测试

- `smoke-p89`（新，复审返修后 **41 条**）：默认不建边、两条都有入选资格、拒绝后都现行、确认走专用接口并清标记、歧义保留全部候选、auto 仍可用、二次确认被拒；F87 之后又加了拒绝后旧确认、陈旧/缺失 ETag、持锁 409、提案写失败四组反例。

## 八、F87 复审返修（2026-11-09，以本节为准）

复审在 `fe2f3d0` 上给出 3 个阻塞项 + 3 个 P2。逐条处理如下，全部有回归钉住。

### 8.1 F87-01 拒绝后的旧确认仍能生效

**根因有两层**：确认走通用修订接口，那里只校验修订关系，不知道提案状态；而 `etagOf` 不包含 `review` / `proposedSupersedes`，所以拒绝之后 ETag 不变，旧页面拦不住。

**修法**（三层，缺一层都还能漏）：

1. **专用确认接口** `POST /supersede-proposals/<id>/confirm`：提交时重新判定"仍待确认、目标仍在候选里、目标仍存活、这条边还不存在、ETag 未变"，全部在写锁内完成；
2. **`etagOf` 纳入提案状态**（`review`、`proposedSupersedes`、`rejectedSupersedes`、`supersedeRejectedAt/ConfirmedAt`），任何提案状态变化都会让旧 ETag 失效；
3. **拒绝留下墓碑** `rejectedSupersedes:[targetId]`，通用修订接口对**这一对**返回 409（其它手改不受影响），所以"旧页面直接打通用接口"这条路也被堵住。

确认接口**强制要求 `etag`**（缺了返回 `proposal-missing-etag`）：状态校验是第一道，ETag 负责"因为别的原因过期"（改名、二次提案、另一个标签页）。

回归（`p89`）：拒绝后 confirm → `proposal-rejected`；拒绝后走通用修订接口 → `proposal-rejected`；陈旧 ETag → `proposal-stale`；缺 ETag → `proposal-missing-etag`；二次确认 → `proposal-not-pending`。

**一处设计修正**：同一事实**再次被提案**时会清掉旧墓碑（用户又改回来是新的意图）。防旧页面靠的是 ETag，不是永久墓碑。

### 8.2 F87-02 新写接口没有工作区锁

确认属实，且是本报告初版写错了：外层 `withWorkspaceLock` 只包了三条导入路由，`withWorkspaceQueue` 是**进程内**队列，跨进程不生效。

**修法**：把 `/nodes/<id>/supersede`、`/nodes/<id>/supersession/revoke`、`/supersede-proposals/<id>/confirm`、`/supersede-proposals/<id>/reject` 四类写路由并入外层锁；持有写锁时统一返回 409 `WORKSPACE_WRITE_BUSY`。

回归：`p89` 在测试进程内真的持有 `.dsh/trivium-write.lock`，再发 reject，断言 409 且状态未变。

### 8.3 F87-03 提案状态写入失败被错误处理

两个方向都修了：

- **创建侧**：`proposeSupersede` 不再吞掉 `sink.update` 的异常。写失败时报告 `skipped:"proposal-failed"`（进 `supersedeSkipped` 计数），**不再**报告 `proposed`；事实本身照常写入。回归：`p89` 用会抛错的 writer 注入，断言状态里出现 `proposal-failed`、没有 `proposed`、面板列表为空。
- **确认侧**：边是唯一持久结果，清标记失败**不再返回 500**（那会让调用方以为什么都没发生，而边已经存在）。现在返回 200 + `warning:"marker-not-cleared: …"`，并在列表侧不受影响（有出边的节点本就不在待确认列表里）。

## 九、第二轮复审返修（2026-11-10）

复审在 `1e08e08` 上给出两个仍阻塞的问题与两个 P2。逐条：

### 9.1 F87-01 同一事件重放会撤销人工拒绝

**根因**：`proposeSupersede` 每次提案都无条件清墓碑。宿主重试一个窗口时是**同一个事件**
（相同 session/seq/messageId），却被当成新意图，节点复用 → 墓碑清掉 → 提案复活 → 旧 generic
请求（无 ETag）又能建边。

**改法**（区分事件代次）：

- 提案节点记录 `supersedeProposedFor`（`message:<id>` 或 `seq:<n>:<sessionId>`）；
- 相同事件：若已拒绝 → 报 `skipped: "proposal-rejected-replay"`，**不动墓碑、不进列表**；若仍待确认 → 幂等，不写库；
- 只有**可识别且不同**的新事件才算新代次，允许清墓碑重新提案；
- 无法识别事件（宿主没给 id/seq）时保守处理：沿用上一次结果，拒绝保持拒绝。

   回归：拒绝 → 用同一 `messageId` 重放 → `proposal-rejected-replay`、列表仍空、墓碑仍在；
   换一个 `messageId` → 重新提案（新代次）。

**另外**：generic `/nodes/<old>/supersede` 现在对**任何待确认提案**都拒绝（`proposal-requires-confirm`），
不再只看"目标是否在候选里"——提案类确认只能走带 ETag 的确认接口。

### 9.2 F87-03 提案存储失败仍被当作恢复成功

**根因**：`runExtract` 的成功条件只看 `llmFailed`，提案失败虽然报出来了，窗口仍被消费
（`pendingWindows: 0`），于是 `recovery: "succeeded"`、提案永久丢失。

**改法**：抽出 `extractOutcome(result)`——`proposal-failed` 与 `llmFailed` 一样使这次运行"未完成"：

- `consume=false`：窗口保留，`lastExtract.skippedBy = "proposal-failed"`、`proposalPending = true`；
- `recovered=false`：不写"已自愈"，因为这次运行并没有完整成功；
- 重放时事实按合并处理，提案在存储恢复后补上。

   回归：故障注入 → `proposal-failed`；解除注入后重放 → 生成一条提案、列表可见、节点数不变（不重复）。
   另断言 `extractOutcome` 对两种输入分别返回 `consume=false/true`。

### 9.8 C2：日期解析扩到"无歧义"为止

`lib/until.js` 原来只认 `YYYY-MM-DD`，而"编造日期"守卫（`lib/date-parse.js`）已经认
`YYYY/MM/DD`、`YYYY.MM.DD`、`YYYY年M月D日`。同一串日期，写进正文能被识别，写进 `until`
却解析不出过期时间——两套解析器各走各的。

改法：`until` 改为复用 `absoluteDateAtStart`（同一个模块），并补两类**无歧义**写法：

- 英文月份：`November 20, 2026`、`20 Nov 2026`（正文守卫与 `until` 同时支持）；
- 分隔符变体与中文日期沿用原有规则。

**不做**：所有年在末尾的纯数字写法。`04/06/2026` 有月/日歧义；`11/20/2026` 虽然只能按月/日
解释，也按同一语法边界拒绝，不从数值推断地区。也不做时区推断
（仍按 `Asia/Shanghai` 锚点、`until` 落到 UTC 日末）。

回归加在既有脚本里，不新增文件（`scripts/` 仍 119）：

  `11/20/2026` 与 `2026-13-01` 必须解析为 `undefined`；
- `smoke-p49`：窗口里写 `November 20, 2026`，候选写成 `Nov 20, 2026` → 不调整（跨写法授权）；
