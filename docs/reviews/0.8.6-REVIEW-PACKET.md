## 一、用户能感知的行为变化

### 1. 增量地图注入（本版最有价值的一项）

会话内短地图带版本：没变化 → **0 token**；有变化 → 摘要 + ≤6 行差异；每 6 轮强制一次全量。

真机实测（2026-11-06，单用户轮次内）：

| 事件 | mode | reason | tokens | turnsSince |
|---|---|---|---:|---:|
| 会话启动 | full | session-start | 123 | 0 |
| 同一轮第 1 个 pre-step | skip | unchanged | 0 | 1 |
| 同一轮第 2 个 pre-step（模型写过 1 条） | diff | changed | **42** | 2 |
| 同一轮第 3 个 pre-step | skip | unchanged | 0 | 3 |

- **当时是失败的**：一轮用户对话里 `turnsSince` 走了 **+3**（两次复现），意味着每两轮就强制
  一次全量，而不是每六轮。
- 根因：`refreshShortMap` 的守卫只跳过**相等**的轮次键，而工具循环的后续 pre-step 不带用户
  消息、`mapTurnKeyOf` 返回空串，空串与任何键都不相等 → 每个这样的 pre-step 都算一轮。
- 这是**同一个坑的第二半**：2026-11-05 那轮已经发现"空键被当成新一轮会让每轮 300 token 的
  预算被重置"，修的是 `lib/turn-ledger.js` 的 `resolveTurnKeyForLedger`（空键 carry-forward），
  `smoke-p86` 也钉住了那一半；但地图那一半的守卫写成了 `turnKey && ...`，空键仍然穿透。
- 已修（`38a91ff`）：空键 = "仍在已打开的那一轮"，与 `lib/turn-ledger.js` 的
  `resolveTurnKeyForLedger` 是同一规则；对"从没拿到过键的宿主"保留一次计数的口子。
- **修复只在单测层验证**：`smoke-p74` 29 → 33 条；把守卫改回旧的一行，p74 掉到 **31/33**
  （`4 !== 3`，多注入了一次）。**没有在真实宿主上复测**（要再花一次模型调用）。

### 2. 待补写队列 + 运行诊断（诚实性最容易出问题的地方）

- 抢锁失败 / 抽取失败 / 被中断的窗口以前只躺在文件里；现在「运行记录」页有**待补写**卡片
  （窗口数、事件数、文件更新时间、每个窗口 80 字预览），对应 `GET /api/dsh-trivium/pending`。
- `stuck` / `recovered` 成对出现在变更记录里；面板有诊断卡，**没有观测值就显示「没有记录」，
  不显示 0**。
- 真机（2026-11-06）：用一个**存活进程**占锁 → 抽取如实报 `lock-busy`（`applied:0`、不等待、
  不编造），窗口留在 `trivium-pending.json`；卡片读出 `1 个窗口 · 51 条事件 · 已确认 144 ·
  文件更新于 05:38:44`，与接口（`windows:1 / turns:51 / acknowledged:144 / updatedAt 05:38:44.942Z`）
  和文件三方一致。
- 顺带一条行为证据：模型在那轮反复重试 `ctx_remember`，每次都拿到 `workspace write busy`
  （它自己写的登记文件里记了 6 条 attempts），没有谎称写入成功，而是把意图写进 `.tmp/` 下的
  登记文件并说明"没写成"。

### 3. 批量写入

`runDeferredWrites` + `flushWorkspaceDb`：多个变更共用极少数 flush。导入 22 条从
**2020 ms / 47 次 flush** 降到 **110 ms / 2 次**（这是 **2026-11-05 那轮的测量，本次没有复测**）。

本次真机只测到一个更小的口径：隔离工作区导入一份 24 行 `CLAUDE.md` → **259 ms**，
`created 4 / linked 4 / skipped 7`，节点 1 → 5。这个数字**不能**用来说明批量写入的吞吐。

### 4. 短地图热度（B2）

被 `ctx_find` / `ctx_read` 命中过的事实获得热度，优先占槽位。热度写在
`.dsh/trivium-usage.json` 旁路文件，**每工作区 60 秒最多重写一次**，文件坏了降级为"无热度"。

真机（2026-11-06，前后对比）：条目 13 → 16；`3:6→7 / 4:7→8 / 5:6→7 / 8:2→4 / 15:8→9`，
一次性 `updatedAt`（05:36:45），与设计一致。

- **只验到落盘与节流，没有验排序效果**（"热度有没有让地图更准"这次没有对照）。
- 已知缺口：**删节点不清热度边车里的条目**，热榜会留幽灵条目（不影响正确性，只影响排序信号）。

### 5. 事件快筛（**保留代码，但不作为本版卖点**）

`screenTurns` 给事件打 0/1/2 分，**整窗 0 分时消费窗口、不发起抽取调用**；某 0 分事件所在
轮次若有工具调用会被**升到 1 分**；0 分只剩空输入、纯标点、`继续/好的/ok` 这类填充语、寒暄。

- 真机两种结局都复现了：
  - 整窗丢弃：`skippedBy:"screen"`、`screenedOut:1`、`audit[0]={rule:"filler",score:0,dropped:true}`、
    `gate.reason:"screen-empty"`；
  - 0 分被工具证据保留：用户文本 `继续` 纯函数得 0 分，同窗口 `gate.reason:"tool-evidence"`、
    `screenedOut:0`。
- **但它省不到钱**：命令类语料 30 → 30（0.0%）；真机上模型每轮都会调 `ctx_find`（连 `ok`
  都调），工具证据把窗口救回来，"整窗丢弃"只在**用户主动中止轮次**时才出现。
- 因此发布说明里明确写了"保留，不作为本版卖点 / 不宣称省调用"（`docs/release-0.8.6.md`）。
  请评审这一处理是否足够——它仍然会**静默丢弃**窗口，且没有事后回收入口。

## 五、我自己认为最可能出事的三处

1. **`turnsSince` 修复没在真实宿主复测**。修法有单测和反向验证，但真实宿主的键序列是我推断的
   （"第一个 pre-step 一定带用户消息"）。如果推断错，症状仍然是每两轮一次全量——只多花 token，
   不丢数据，但发布说明里"每 6 轮强制一次全量"就成了空话。
2. **快筛静默丢窗口**。它现在不省调用，却保留了"整窗 0 分直接消费掉、没有回收入口"的风险面。
   保留它的理由只有"边界窄 + 有 gate 兜底"，一旦白名单被后人放宽，代价是静默丢事实。
3. **热心打包未使用代码**（`identity/router/inherit/memory-writer`）。它们现在零调用方，
   但只要有人翻到开关打开 `identityMerge`，就会遇到没有语料校准的合并阈值。

## 六、给评审者的具体问题

1. 一轮 +3 的修复（空键视为同一轮）是否可辩护？有没有更稳的轮次身份（例如由宿主事件
   而不是消息窗口推导）？"未在真机复测"是否阻塞发布？
2. 快筛：既然实测省调用 0%，**留着**和**删掉**哪个更符合"不宣传但要诚实"？如果留着，
   发布说明里的措辞够不够？
3. `identityMerge` / Router / inherit / MemoryWriter 该不该随这个版本打包？如果该留，
   要不要在包里显式标注"未使用/实验"？
4. `lib/store.js` 的批量写（`runDeferredWrites`）在**部分失败**时的语义是否清楚？
   （一个 batch 里第 3 条失败，前 2 条是否已落盘、pending 是否保留、调用方能否分辨？）
5. 待补写卡片 / `GET /pending` 只读不写，**没有"现在重试"入口**——这是设计选择还是缺口？
6. `mapInjections.full` 与 `lastScreen.counts` 两处口径（§三 5、6）要不要在发布前修掉？
   它们是诊断字段，但验收时正是靠它们取证，读错会得出相反结论。
7. `docs/release-0.8.6.md` 的口径是否与实现一致？（尤其"每 6 轮强制一次全量"、
