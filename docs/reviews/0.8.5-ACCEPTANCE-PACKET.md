# 0.8.5 验收包（供 Astra 复审）

> 目标：让一个不了解上下文的评审者，在**半小时内**判断这个版本能不能发。
> 与上一轮送审的 0.8.5 不同：这一版**只有内核升级**，管线改动全部移到 0.8.6，
> 所以需要审的东西从"六项行为改动 + 一个内核"缩到"一个依赖升级 + 一个适配函数"。

- 分支：`release/0.8.5`（从 `d83450c` 拉出，0.8.4 的发布基线）
- 版本：`0.8.5`；内核：`triviumdb` `0.9.0-beta.3` → **`0.9.0`**
- 改动面：**11 个文件**（含文档与证据），其中源码只有 `lib/store.js` 一处新增函数
- 基线回归：**74/74**（0.8.4 那套，一个用例都没改）
- 未打 tag、未发布

## 一、这个版本做了什么（全部）

| # | 改动 | 位置 |
|---|---|---|
| 1 | 依赖从 `0.9.0-beta.3` 升到 `0.9.0` | `package.json` / `package-lock.json` |
| 2 | 写入前清理 `undefined`（0.9.0 会拒绝） | `lib/store.js`：`pruneForStorage` + `hardenEngine` |
| 3 | peer 包自愈（`npm install` 会删掉宿主的两份 peer） | `scripts/link-peers.mjs` + `run-all.mjs` 启动时调用 |
| 4 | 升级/回退演练脚本与证据 | `scripts/verify-kernel-upgrade.mjs`、`docs/evidence/kernel-upgrade-2026-11-05/` |
| 5 | 发布说明与版本文案 | `docs/release-0.8.5.md`、两个 README |

**没有**：事件快筛、地图热度、增量注入与新轮次键、事实身份、批量写入、新诊断、`MemoryWriter`、
`scope`/`inherit`/Router。这些都在 `main` 上，属于 0.8.6。

## 二、唯一的行为风险：`pruneForStorage`

0.9.0 的类型化存储拒绝 `undefined`：

```
undefined cannot be represented as a serde_json::Value
```

beta.3 是静默丢弃。我们的 payload 大量由"展开可选字段"构造，所以适配放在**引擎边界**——按
`triviumdb.d.ts` 的写面包一层：

```
insert / insertWithId / updatePayload / updateEdge / commitTransaction
```

规则：

| 输入 | 输出 | 为什么 |
|---|---|---|
| 对象里的 `undefined` 键 | 删除该键 | 与 beta.3 的行为一致 |
| **数组里的 `undefined` 元素** | **`null`**（保位） | 上一轮复审指出：第一版用 `filter` 把 `[1, undefined, 3]` 变成 `[1, 3]`，改变了位置语义 |
| 函数 / symbol | 丢弃 | JSON 里没有它们的表示 |

这一条请重点看：它是这个版本唯一可能改变写入内容的地方。

## 三、验收证据（全部可复跑）

```bash
node scripts/run-all.mjs                                    # 74/74
node scripts/verify-kernel-upgrade.mjs <含 trivium.tdb* 的目录> --expect-kernel=0.9.0
node scripts/verify-kernel-upgrade.mjs <同一目录> --probe --expect-kernel=0.9.0-beta.3   # 回退
npm pack --dry-run                                          # 44 个文件 / 223.7 kB
```

JSON 证据在 `docs/evidence/kernel-upgrade-2026-11-05/`：

| 文件 | 断言 | 结果 |
|---|---|---|
| `upgrade-0.9.0.json` | `kernel=0.9.0`、`kernelMatches=true` | 打开历史库 → 写入 → 重开 → 恢复升级前备份，`nodeDigest`/`edgeDigest` 与升级前一致 |
| `rollback-beta3.json` | `kernel=0.9.0-beta.3`、`kernelMatches=true` | 旧内核能打开**升级前**的备份（16 节点） |

`--expect-kernel` 是**真判定**，不是记录：版本不符时 `ok:false`、`error` 写明期望与实际、退出码 1
（上一轮复审复现过它只记录不判定，已修）。

内容比对用的是**全量 payload 的 sha256**（含 `history`）与**边端点+标签**的摘要，不是"前 60 字"。
证据里只有目录名与摘要，无本机路径（扫描 `C:\` / `Users\` / 用户名 → 0 命中）。

## 四、必须写进发布说明的不可逆点

0.9.0 把库文件版本升到 **v10**，`0.9.0-beta.3` 打开时报 `TDB_UNSUPPORTED_DATABASE_VERSION`（可读 v5..=v9）。

因此：

1. **降级插件不是回退**，恢复备份才是；
2. 备份必须复制**整个文件组**（`triviumdb` 的 `.tdb` + `.gidx` `.pidx` `.pld.*` `.text` `.text.meta`
   `.vec` `.wal` `.lock` `.flush_ok`），只复制 `.tdb` 会得到 `TDB_CORRUPTED_FILE`；
3. 备份时关闭插件，避免读到写了一半的文件组。

这三条已经写进 `docs/release-0.8.5.md` 的引用块。

## 五、已知限制（不掩盖）

1. 演练只用了一个库（仓库工作区，16 节点 / 17 边）；没有跨机恢复，也没有 `0.8.11` 的降级测试。
2. 0.9.0 的**批量写入路径更慢**（同一基准 p95 206 → 483 ms），但本版本不含批量写入，
   这条影响会在 0.8.6 处理。
3. `p60` 在历史运行中发生过一次原生崩溃（`exit 3221226505`），本轮 74/74 全过，未复现；保留为已知问题。
4. `pruneForStorage` 是边界兜底：调用点仍在构造带 `undefined` 的 payload，只是被吃掉了。
   长期应逐步收敛到构造处，但不属于本次发布范围。

## 六、给评审者的具体问题

1. `pruneForStorage` 的数组策略（`undefined → null` 保位）是否可接受？还有别的边界
   （`NaN`、`Infinity`、`BigInt`、循环引用、`Date`、`Map`）需要显式处理吗？
2. 在引擎边界兜底、而不是修调用点，这个折中在"只发内核升级"的版本里可以接受吗？
3. v10 不可逆 + 只能靠备份回退，这个风险是否已经被发布说明充分告知？
4. 74/74 的基线回归是否足以支撑"行为不变"？还应补哪一条内核专项断言？
5. 还有哪些地方会因为这次内核升级而**静默**改变语义（例如索引、向量、WAL 恢复）？
