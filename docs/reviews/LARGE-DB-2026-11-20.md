# 大库读取实测（2026-11-20）

P2-B 的结论是"按实测决定是否做分页/异步"。本轮先测，结论是**暂不需要**：读取耗时由"范围内的 900 条事实"决定，与库总量基本无关。

## 1. 方法

`node scripts/measure-large-db.mjs --sizes 5000,20000 --reps 12`

- 合成库：1 个实体 `#101` + 900 条一跳事实 + 其余为无关背景节点（5,000 / 20,000 总量）。
- 每次请求换一个问题文本，避免命中查询缓存（首次测量用了固定问题，p50 0.04 ms 是缓存，已改掉）。
- 计时路径：实体范围检索（词面，`limit:5`）、同一检索加 `packTokens:300`、`allNodeIds()`（面板节点数的来源）。
- 环境：本机 Windows / Node 24 / TDB 0.9.2，临时目录，未调用模型或 embedding。

## 2. 结果

| 库规模 | 磁盘 | 建库 | 检索 p50 | 检索 p95 | 加记忆包 p50 | 加记忆包 p95 | 节点数 p50 | 预算拒绝 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 5,000 | 32 MB | 2.4 s | 50.7 ms | 62.7 ms | 56.1 ms | 59.0 ms | 0.27 ms | 0 |
| 20,000 | 128 MB | 9.5 s | 50.2 ms | 54.4 ms | 55.1 ms | 58.1 ms | 1.04 ms | 0 |

## 3. 结论

1. **库总量不是瓶颈**：从 5k 到 20k，检索耗时不变（约 50–60 ms），因为范围只覆盖 900 条一跳事实。`allNodeIds()` 从 0.27 ms 升到 1.04 ms，仍然可忽略。
2. **瓶颈是固定预算**：`ENTITY_SEARCH_LIMITS.nodes = 1000`。范围一旦超过 1000 个一跳节点就直接 422（见[面板错误态](PANEL-ERROR-STATES-2026-11-20.md)），而不是变慢。
3. 因此现在做**分页/异步游标没有可测收益**：900 条范围在 150 ms CPU 窗口内，20k 库也不慢。真正需要分页的场景是"一个实体挂了上千条事实"，而当前行为是明确报错，不是卡死。

## 4. 什么时候改变结论

- 出现真实工作区里**单个实体 > 1000 条事实**（现在会 422）：那时需要"分页 + 显式继续"，并且要重新测 p95 与拒绝率。
- 出现**多跳**或全图扫描需求：当前只做双向一跳，未测多跳成本。
- 出现**并发多读**：单进程同步执行，读请求天然排队；本轮没有测并发（见错误态报告里的 429 未复现）。
