## 五项重点复现

| 项目 | 观察与判定 |
|---|---|
| 1. A 的提案令牌打 B | **普通 A/B 通过。** 两库节点 ID、名称、正文、节点级 ETag 相同。A 的令牌在 B 确认和拒绝均为 `409 proposal-stale`，两个提案都保留。在真实宿主延迟 A 的列表直到 B 已显示，再释放 A。页面只显示 B 的原句，“保持原样”发送 B 的令牌与 cwd。目录名反例见 F88-R02。 |
| 2. 确认与拒绝审计 | **各生成一行，内容部分失败。** 同一工作区处理两条不同提案，两个 POST 都是 200，一个 `GET /changes` 同时返回 `supersede-confirmed` 与 `supersede-rejected`。确认行的提案 ID 和目标 ID 正确。拒绝行给出错误的候选数，且独立操作可能在列表中消失，见 F88-R05。 |
| 3. 子进程持工作区锁 | **六条通过。** 等不同 PID 返回持锁信号，再发编辑、合并、归档、删除、提案确认、拒绝六个 POST。全部返回 `409 WORKSPACE_WRITE_BUSY`，比较全部节点及关系，状态一致。子进程释放并退出后编辑返回 200，读回“释放后新名”。芯片另有写库入口，见 F88-R03。 |
| 4. 中途失败的外部导入 | **位置和三个分支通过，零值和总回执语义失败。** 在独立宿主进程对三个合成库的写入方法注入故障，由面板真实点击 `import-external`。三次均返回 HTTP 500、`partial=true`，净增量分别为 2、0、null。按钮下方显示三种不同文案，均无“被拒绝”。停止宿主并只读重开后，三个库的业务节点分别为 2、1、1。零值库原有的 1 个节点已被合并更新，见 F88-R04。 |
| 5. 两档视口与交互稿 | **主要排布通过，交互部分符合。** 用真实发布包走查 760px、1440px 视口，并补看内容宽 420px、822px 和 1112px。其物理布局、操作可达性和与设计稿的差异见下表。 |

## 阻塞项与复现步骤

### F88-R01　普通记忆删除仍可串库

1. 在两个普通中文工作区创建不同正文的记忆，令其获得相同数字 ID。在甲库打开「记忆库」。
2. 切到乙库，只延迟乙库的 `GET /nodes` 响应，让状态请求正常返回。选择器已经显示乙库，甲库旧列表仍然可见。
3. 展开旧行，点击删除。确认框明确显示“甲库专用检查项，交接前请复查”。点确认，实际 POST 却带乙库 cwd，服务端返回 200。
4. 分别回读两个库。甲库条目仍在，乙库条目消失。在另外一对工作区重做一次，结果相同，两次命中的 ID 分别为 5 和 4。[真实确认框](evidence-0.8.8/wrong-delete-confirm.png)

切库已清除展开状态和提案，却保留 `nodes`，普通行操作提交时从当前选择器取 cwd。修复应在切库时同步清空旧行及其确认框，将行来源和操作绑定，提交前核对仍是用户看到的库和对象。按上述时序验收，两库都应保留原条目。[切库与行写入实现](../../lib/client.js)

### F88-R02　不同物理目录可能得到相同的提案令牌

在 Windows 的同一临时父目录下建立 `İ`（U+0130）和 `i̇`（U+0069、U+0307）两个目录。文件标识不同，两库各自有同 ID、同正文的提案。令牌计算对 cwd 调用 `toLowerCase()`，这两个输入得到相同字符串和令牌。拿第一库的令牌拒绝第二库，真实 HTTP 返回 200，第一库待确认数仍为 1，第二库变为 0。应使用能区分真实库的规范标识，并保留客户端的切库防护。[提案令牌](../../lib/supersede-review.js)

### F88-R03　芯片可以绕过同一把锁删除节点

保持上述子进程写锁，同一给定工作区上 `POST /chips` 返回 200，节点净增 1。随后 `POST /chips/batch` 提交 `action=delete` 和该 ID，返回 200，读库确认该节点已删除。这两个入口会写主图库。应让芯片新增和批量归档、删除遵守与面板节点写入相同的互斥规则。[芯片路由](../../lib/server.js) · [实际写库操作](../../lib/pins.js)

### F88-R04、F88-R05、F88-R07　界面和审计还会误报结果

- **F88-R04，部分导入。** 在已存在第一条事实的库中，先合并该事实，再让下一条插入抛错。净增为 0，旧节点的 `updatedAt` 和持久化负载已变化。按钮下方却写“中断前没有写入任何条目”。三种中断的页首回执也都标为绿色“✓ 已提交”。按设计稿应显示“新增 0 条，已有记忆可能发生过合并”，用独立的部分提交状态。N 是净新增数，无法推出其余候选均未处理。[零值回执实拍](evidence-0.8.8/partial-zero.png) · [后端计数契约](../../lib/markdown.js)
- **F88-R05，审计身份和内容。** 拒绝两个候选时接口返回 `rejectedTargets=[2,3]`，日志却从 `result.targets` 取值，写成 `0 candidate(s)` 且没有候选 ID。拒绝不产生退役事实，记录应列出保留的候选。用同一提案节点构造第二个有效事件，两次有效拒绝都返回 200、原始文件有两行，`GET /changes` 因固定 `opId=reject:<id>` 只显示一行。原事件原样重试仍正确返回 409。确认路径又把必填 ETag 当作面板来源证明，直接 HTTP 也写为 `via panel`，给定的操作 ID 没有进入审计行。应记录真实入口、候选和本次操作的标识。[路由记录](../../lib/server.js) · [读取时去重](../../lib/change-log.js)
- **F88-R07，迟到的状态回执。** 在现有组件夹具中加载包内客户端，先显示 B 的待补写列表，再回送延迟的 A 响应，B 卡片出现 A 的预览文本。另一次让 B 的拒绝成功响应在切到 A 后抵达，A 的待确认提案旁出现 B 的“已保持原样”。这两项是显示串库，提案写请求实际指向 B。待补写读取和写操作完成后的提示也要校验工作区与请求代次。[面板实现](../../lib/client.js)

## 交接包第五节的四个判断

1. **工作区令牌是必要防线，当前实现仍不充分。** 普通目录的提案修复通过客户端、HTTP 与真宿主验证。目录标识仍有 F88-R02 的碰撞。显式传未知 cwd 的 `/status` 返回空 cwd，提案列表返回 400。省略 cwd 才读取活动库，而显式读取 B 的状态也会把进程活动库切到 B。写操作应绑定屏幕上那条数据的来源。普通删除及其他可见状态分别见 F88-R01、R07。
2. **接受先落动作、后写审计，以及审计失败单独警告。** 人为持有独立的审计锁后，拒绝返回 200 和 `audit-not-recorded: audit-lock-busy`，提案已处理，`/changes` 的 `incomplete` 为 true。此时把整个动作报失败会诱发错误重试。F88-R05 的真实目标和事件标识仍需修正。
3. **按实际写入对象决定锁边界。** 单纯写设置、pin 或旁路文件，可以采用其各自的同步机制。足以新增、归档或删除主库事实的芯片路由应纳入工作区锁。长时间的 map/backfill、map/cut、embed-backfill 可以避免全程占交互锁，仍需为实际写入段提供互斥或分批提交的证据。对这些管理任务，本轮结论来自源码审查，未做长任务并发验收。
4. **p24、p26 保留了原有失败路径断言。** 对两个标签逐项比较，用例名称及数量分别都是 12→12、19→19。差异是先展开再执行原测试，原有 409、取消不发请求和目标 cwd 等检查均在。p24 额外增加了 `openRow` 的行存在性断言，断言调用点 37→38，超出本机“冻结、不扩充断言”的口径。p26 调用点 125→125。交接包中的 9→12、16→19 不符合这两个标签之间的差异。这些既有用例没有覆盖旧库普通记忆行在切库期间仍可删除的时序。[p24](../../scripts/smoke-p24.mjs) · [p26](../../scripts/smoke-p26.mjs)
