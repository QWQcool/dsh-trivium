## 仍需验证或单独决策的边界

1. **更正调度。** pins 先占用每轮 300 预算，更正排在其后；固定 pins 持续占满时，更正可能持续延期。关闭 chips 与 recall 后，pre-step 会提前返回，已排队更正不会继续发送。本轮没有擅自改变已有优先级和开关语义，下一轮应给出最长延迟与状态提示的明确契约。
2. **自然到期。** 目前更正主要由写事件触发。无写操作、仅时间越过 `untilAt` 的已投递事实，需要独立的时间推进/真实宿主测试，不能根据写后更正通过就声称已经覆盖。
3. **旁路健康按工作区展示。** 当前 `sidecarHealth()` 是进程级状态；另一工作区的成功操作可能覆盖此前失败提示。应改为按工作区保存并展示 health，避免误导用户排障。
4. **索引失败与性能。** 文本索引写入/重建有宽泛异常降级，关键词兜底能掩盖索引问题。需要独立指标和故障可观测性。逐节点重建索引、导入与检索扫描的负载影响应先定数据规模与阈值再测，本轮没有性能结论。
5. **宿主与发布层。** 源码驱动的真实 peer 验证、离线原生库测试、真实桌面 UI、独立 tarball 安装是不同层。本轮每一层分别记录；两个独立浏览器进程的冲突场景、宿主 UI 触发派生失败仍不能由上述单元/集成结果代替。

## 设计判断

- 四工具、默认少注入、工作区独立数据库、人工确认替代、只读体检与显式维护工具都有清晰职责，值得保留。
- 当前最有价值的收敛是 **减少同一规则的多份实现**。B01 说明 JSON 与 JSONL 各自维护导入逻辑会产生正确性分叉；本轮已将它们合到共同事务入口，保留各自的合并/快照同步语义。
- 后续可清理但不应与缺陷修复混做：`cwdForDb` / `cwdOfDb` 重复查表；运行时与预览重复的候选/trace 投影；单文件 `store.js` 与客户端 bundle 的职责过多。应先按导入、检索、诊断拆职责，再考虑增加能力。
- 每会话账本、pending/sent 更正、短地图缓存并非天然冗余：它们分别回答“送过什么”“事实是否失效”“启动时已有何上下文”。需要的是清楚的生命周期与观测，而不是简单删掉其中一层。
