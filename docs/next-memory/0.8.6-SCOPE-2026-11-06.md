## 3. 发布前建议先做（都很小）

**P1（已完成）`turnsSince` 一轮只走 1。**
根因确认：`refreshShortMap` 的守卫只跳过*相等*的 key，而工具循环的后续 pre-step 不带用户
消息（`mapTurnKeyOf` 返回 `""`），`""` 与任何 key 都不相等，于是每个这样的 pre-step 都
加一次。修法：把空 key 当「同一轮的后续」，与 `lib/turn-ledger.js` 的
`resolveTurnKeyForLedger` 用同一条规则；对"从没拿到过 key 的宿主"保留一次计数的口子。
第一轮回归在 `scripts/smoke-p74.mjs`（29 → 33 条），反向验证掉到 31/33。
复审（F86-01）又找出两处遗漏并已补齐：`previous.turnKey` 会被写成 `""`，无法区分
「第一次空观察」与「处理过的空观察」；`mapTurnKeyOf` 只读 `last.text`，而 DSH v4 把正文
放在 `content[]`。改用 `sawTurnKey` 锚点 + `content[]` 文本回退，`p74` 33→36、`p86` 15→16。
全量 89/89。细节见验收文档 §9 与评审包 §九。

**复审的另外三项也已返修**：F86-02 损坏 pending 明确失败（`500 / ok:false`）、
F86-03 批量部分提交回执（`partial / newNodesBeforeFailure / retryHint`）、
F86-04 申报口径（中英发布说明与评审包）。对应回归在 `p82` / `p83` / `p87`。

**P2（建议做）`lastScreen` 补一个"0 分被工具证据保留"的计数。**
现在只能靠"用户原文 + 纯函数 + `gate.reason`"三条线拼出这个结论（见验收文档 §1.2），
`counts` 读的是工具提升之后的组分数，`audit` 只收最终仍为 0 的组。加一个
`keptByToolEvidence: n` 就能自证，成本极低。

**P3（顺带）两个口径/清理小口子。**
(a) `mapInjections.full` 不含 session-start 的 full，按名字读会少算，建议补计或改名；
(b) 删节点不清 `.dsh/trivium-usage.json` 里的条目，热榜会留幽灵条目，建议在删除路径
顺手清，或在读取时按现有节点过滤。

## 4. 不建议现在做的事

- **不要为了提高"省调用"数字去扩快筛白名单**。2026-11-04 那次已经把命令/路径一类规则删了
  （理由是"形状不证明无事实"），这次实测也没有可省的空间：真实窗口几乎都带工具轮。
- **不要在没有语料校准的情况下开 `identityMerge`**。合并是写路径上的不可逆操作，比漏存更难
  收拾。
- **不要拿这次的 ¥0.88 当账单，也不要称为已证明的上界**。那是按"每请求 12k 输入 token"
  这个**未核实假设**算出的峰价估算（宿主这几场的 `usage` 没落盘），实际值可能更高或更低。

## 5. 与用户既定路线的差异

用户原话是"只发 增量地图 + 待补写/诊断 + 批量写入 + 热度；快筛保留但不宣传；身份与
Router 顺延"。本次证据支持这个方向，唯一要加的前置条件是把 `turnsSince` 修掉再发增量地图
——否则发出去的正是 11-04 已经修过一次、这次又复发的那个洞。**这条前置条件已完成**
（§3 P1），所以现在按原方向直接切范围即可。
