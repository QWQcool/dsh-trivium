## 1. 结论修正

| 原结论 | 复核后结论 |
|---|---|
| 36.7%→100%是准确率，图相对纯文本稳定零增益 | 撤回因果与等效结论。判据有明确假阳性；在线脚本所有场景/臂/重复共用同一库；本机未收到原始在线JSON，无法独立重判 |
| 14.7倍token | 14.7是¥0.2153/¥0.0146的脚本估算费用比，不是token比或供应商账单；分臂usage未回交 |
| “9次比较全部30/30，无抖动，因此等效” | 每臂10场景×3重复；分数饱和、小样本、单模型不能证明零效应或等效 |
| 50k根因只有keywordFallback，约n^1.75 | 全扫存在且显著，但锚点扫描、索引构建与重开也有成本；旧表查询数值不支持n^1.75拟合 |

## 3. 负载判断

旧报告50k查询p95=9.28s、关闭重开=2.27min，若数据真实，则均超过预注册2s/10s门槛。**门槛不调整**；但原始50k JSON未回交，本轮不把历史数字当成本机实测。

本轮单独进程1k诊断：

- keyword区间约94–97ms，占三条查询总时长约53%–87%；entity-anchor区间另约13–35ms。区间包含候选接纳和插桩开销，不是纯函数精确CPU归因。
- 导入1k节点调用buildTextIndex **1000次**；重开重新索引1001个节点，再build一次。
- 插件重开40.66ms；直接内核loadTextIndex:true打开18.35ms且有文本命中。后者绕过插件初始化，只是候选机制，**没有改生产开库方式，不是已验收优化**。
- 建议优先研究持久索引有效性/恢复和批量build，再处理查询全扫/锚点扫描。不能直接删除重建，内核默认不加载文本索引。

旧bench-scale的reopenMs是同进程close+open，不是OS冷启动；peakRssMb是收尾采样，不是真正峰值；tdbMb统计整个.dsh目录。repeat还改变图种子，因此是跨图形态检查，不是同库重复稳定性证明。

## 4. P1 / C4决定

**本轮不启动对手横跑。理由是判据与对照设计不足，不是“已经100%所以没价值”。** 先准备事实项/否定/时态/原因的盲审rubric和完整可复核输出，再比较指定对手。

本机已有Bun **1.4.3**，不能沿用另一机器“缺Bun”的判断。goodmemory、34262315716/dsh-memory及sqlite-vec本轮均未安装/激活验证，状态是**未覆盖**，不是“装不上”；没有换插件充数。OpenViking保持放弃。以后C4仍先隔离装载、固定provider，再跑场景。
