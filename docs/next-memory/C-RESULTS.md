# C 批结果汇总（质量与负载基线）

日期：2026-10-29。基线 `cb2b070` → 本批提交见文末。分支 `main`。
不发布 npm、不改版本号（仍 `0.7.1`）、不加工具、不加服务。

本文件是 C 批的**单一结论入口**。逐项证据与失败样本在各自计划文件里，此处只给数字、判定和边界。

## 1. 一句话结论

**记忆让回答从 36.7% 到 100%，但"图记忆 + 工具检索"相对"把同样事实写成一段文本"没有准确率增益，代价是 14.7 倍 token。**
所以产品的可辩护卖点是**可管理**（更正链、来源、工作区隔离、预算账本、不随事实数线性膨胀），不是"记得更准"。

同一批测量还定位了两个真缺陷（排序按图连通性、抽取成本是注入的 16 倍）并修掉其中一个。

## 2. 负载基线（`scripts/bench-scale.mjs`，合成库，semantic off，Node 22，单机）

每档独立子进程测量（同进程连跑会累加 RSS，导致数字失真）。

| 档 | 导入 | 重开（含 BM25 全量重建） | `.tdb` | RSS 峰值 | 检索 p50 | p95 | 正例 | 负例 |
|---|---|---|---|---|---|---|---|---|
| 1k ×3 | 0.67–0.85 s | 94–148 ms | 6.7 MB | 134 MB | 187–189 ms | 228–275 ms | 15–16/16 | 3/3 |
| 10k ×3 | 35.2–35.3 s | 3.41–3.47 s | 67.3 MB | 568 MB | 1.50–1.51 s | 1.90–1.94 s | 15–16/16 | 3/3 |
| 50k ×1 | **17.5 min** | **2.27 min** | **337 MB** | **1943 MB** | **7.70 s** | **9.28 s** | 15/16 | 3/3 |

按**动手前预注册**的门槛判：50k 档 p95 9.28 s ≫ 2 s → **负载不合格**；重开 2.27 min ≫ 10 s → **冷启动不合格**。10k 档 p95 1.90 s 已接近上限。

- 根因：`keywordFallback`（`lib/store.js`）对 `db.allNodeIds()` 逐节点 `db.get()` + 每 term 一条正则，O(n) 全扫；缩放约 n^1.75。
- 重开成本来自 `openWorkspaceDb` 的 `rebuildTextIndex()` 每次全量重建。

## 3. 注入层与正确性硬门槛（`scripts/bench-injection.mjs`）

真实插件路径（`registerTools` + `plugin.apply` + 真实 `pre-step`），零模型调用。

| 门槛 | 实测 | 阈值 | 结果 |
|---|---|---|---|
| G1 跨工作区泄漏 | 0（6 查询 × 2 路径） | = 0 | ✅ |
| G2 同轮注入预算 | 累计 76 token（第 1 步 76，后续 0） | ≤ 300 | ✅ |
| G3 过时事实 | 标 `stale` ✅；`include_stale:false` 返回空 ✅ | 两者 | ✅ |

**G2 第一版测法是错的**：每次新建用户消息会被判成新的一轮，于是"每步 76、从不累计"，看起来永远合格。真实语义是 `turnKeyOf()` 用宿主 id 或**消息对象身份**判轮。

## 4. 损坏链投影（`scripts/bench-g4.mjs`）

| 用例 | 实测 | 结果 |
|---|---|---|
| 合法链投影 | 当前头 = 最新版；旧正文不出现在 `ctx_find` | ✅ |
| 链上正文改写 | `REVISION_PROTECTED` | ✅ |
| 删除链上节点 | `REVISION_LINKED` | ✅ |
| 环（`supersede` v2→v1） | API 拒绝，`code: cycle` | ✅ |
| 32 跳上限 | 第 33 跳写入即被拒（`too-long`），32 跳链解析正确 | ✅ |
| 绕过 API 造环（`ensureLink`） | **不可构造**，`ensureLink` 拒绝 `supersedes` 标签 | ⚠️ 未覆盖 |

结论：**可构造范围内全过；`resolver` 的 `cycle`/`too-long` 分支代码存在但没有可构造输入**，只能记"未覆盖"，不能记"已验证"。

## 5. 缺陷一：排序第一键是图连通性（已定位，未修）

`lib/store.js` 的最终排序先比 `rankBoost`，而 `rankBoost` 第一条是"有业务边 +4"；相关性 score 只是第二键。

后果：**一个精确名称命中但没有任何业务边的节点，会被 8 个"弱相关但有边"的节点整条挤出 top-8**（不是排后，是消失；`topK` 默认 8）。

- 触发条件：节点入边出边都没有业务边（新建、尚未建立关系的孤立事实）。
- 表现：同一库、同一查询，只改边形态，结果就变；7 次运行复现 4 次。
- 为什么严重：受打击的恰是"刚记住、还没连上关系"的新事实，而这是记忆插件的第一性要求；库越稠密越严重。
- 归属：**D 批候选**。方向是"相关性优先、连通性降为 tiebreak 或小幅加成"，或给精确名称命中一个保底名额。

定位过程中被否证的两个假设：64 候选截断（`onStage` 证明三阶段都含目标）、图扩散加分（A/B 无效，因为 import 的 `from/to` 用旧 id，`{from:3}` 指的不是库 id 3）。

## 6. 缺陷二：抽取成本是注入的 16 倍（已修）

`scripts/bench-extract.mjs`（真实 `distill()` + 桩 llmCall 抓提示词，触发次数用离散事件模拟）：

| 项 | 数值 |
|---|---|
| 单次抽取提示词（40 条消息累积） | 2,175 token |
| 现状触发频率（静默 12 s） | 40 次/天（≈每条用户消息一次）→ 95,000 token/天 |
| 注入侧对照（149/300 × 20 轮） | ≈ 6,000 token/天 |

**修复**（`lib/index.js`）：

| 项 | 旧 | 新 |
|---|---|---|
| 静默窗口 | 12 s | 60 s |
| 批量触发 | 无 | 累积 12 条 turns 立即抽 |
| 冷却 | 无 | 5 min（冷却期内不清空缓冲） |
| 重复抽取 | 无保护 | `turnsHash()` 同一批内容不重复调模型 |

预期降幅约 68%（40 → 13 次/天）。回归：`smoke-p27`（调度策略）、`smoke-p28`（去重）。

## 7. 缺陷三：单字符检索词造成有害注入（已修）

C3-offline 的 S06：问「1+1 等于几」时自动召回投了一条无关实体。

两层原因都要修：

1. `queryTerms` 对 ASCII/数字没有最小长度闸（汉字早有 ≥2），`1` 成了检索词；
2. `primaryScore` / `lexicalScore` 还有原文子串分支 `text.includes(q)`，单字符照样命中。

修复后 `forbidden = 0`。回归：`smoke-p29`。

## 8. 场景材料齐备性（`scripts/bench-c3.mjs`，离线，零模型调用）

10 个 pilot 场景，判据是字符串断言而非模型自评。

| 指标 | 结果 |
|---|---|
| 通过 | **9/10**（门槛 8/10） |
| `forbiddenTotal` | **0** |
| 最大单轮注入 | 213 token（≤300） |
| 越预算 | 0 |

唯一未过：**S09 换述复合**（「按我的偏好和约束，晚上推什么」漏掉"喜欢实际演示"）。两条事实零字面重合，纯词法建不起联系 —— embedding / 术语扩展才能解决，不在 D 的最小范围。

**我自己的两个断言错误**：S05 检查"输出里有节点名"（输出只打正文）、S10 检查"旧正文出现"（正确行为恰恰是不当当前，只报 `matched_history`）。判据写错会让产品看起来更差。

## 9. 端到端（`scripts/bench-c3-online.mjs`，真实模型 `deepseek-chat`）

10 场景 × 3 臂，`temperature=0`，计费取 provider `usage`（不是插件估算）。

### 9.1 单次（n=1，30 格，49 次调用）

| 臂 | 通过 | 成本 |
|---|---|---|
| A 无记忆 | 3/10 | ¥0.0184 |
| C 当前默认（工具循环） | 10/10 | ¥0.0477 |
| E 纯文本对照 | 10/10 | ¥0.0050 |

### 9.2 三次重复（90 格，145 次调用）——正式数字

| 臂 | 通过 | 成本 | 工具调用 |
|---|---|---|---|
| A `nomem` | **11/30（36.7%）** | ¥0.0588 | 0 |
| C `default` | **30/30** | ¥0.2153 | 139（≈4.6 次/对话） |
| E `plain` | **30/30** | ¥0.0146 | 0 |

合计 **¥0.2884**（prompt 84,614 / cache hit 22,912 / completion 19,194）。预算上限 15 元，用掉 1.9%。

- 方差：`default` 与 `plain` 9 次比较全部 30/30，**没有抖动**——"持平"是稳定事实。
- 成本比 `default / plain` ≈ **14.7 倍**（n=1 时算 9.5 倍，重复后更准）。
- 失败的 19 格全在 `nomem`：S01/S02/S04/S05/S08/S09 各 3/3；S07 只败 1/3，那 1 次"通过"是判据假阳性（模型泛泛提到"基线"）。

### 9.3 局限（不许藏）

- 每格 n=3、`temperature=0`、**单一模型**；没有多模型交叉。
- 判据是字符串包含，不是语义判分；同义表述会被判错，泛泛而谈会被判对。
- 10 个场景是我们自己写的，**不是外部金标集**，不能外推成"真实使用质量"。
- `default` 臂限 3 轮工具循环，超过即判失败 —— 这是 harness 上限。

## 10. 方法学教训（这批最贵的产出）

1. **fixture/判据的错会伪装成产品结论**，而且两个方向都会错：假阳性（S01、S07）让人以为没问题，假阴性（S02、S10）让人以为坏了。每次都要看真实输出，不能猜格式。
2. **每个新脚本至少被自己的假设骗过一次**：`payload.body` vs `payload.text`（全零命中）、import 的旧 id 映射（A/B 无效）、同名节点被 `mergeInto` 合并（链没建起来）、同进程 RSS 累加（数字失真）、`settle()` 固定 sleep 太短（去重假失败）。
3. **脚本声称成功不等于改动落地**：`node -e` 字符串替换没命中，却打印了 "instrumented"，白跑一轮。改完必须 grep 验证。
4. **provider 会把工具调用当文本吐出来**（`<｜｜DSML｜｜…>`），还出现过 `ds_safety` 标记；不清洗会把工具标记当最终答案判失败。
5. **测量脚本自己的错，比测出缺陷更危险**：它会让"合格"变成假象。
