## 2. 熔断触发在哪：是 agent 在逛工作区，不是记忆在绕圈

NEGATION 有 **3/10** 轮在**第二个 setup 轮**（内容只有“继续。”）里超过 12 个请求，被熔断标记为 `request-cap`（39–63 秒），费用明显偏高（¥0.036 / ¥0.018 vs 中位数 ¥0.007）。

把这些轮次的报文逐条解开，**循环里调用的不是我们的记忆工具**：

```text
#1 -> [ctx_remember]          ← 记忆写入，一次
#4 -> [get_goal, pwsh]
#5 -> [ctx_find, pwsh]
#6 -> [pwsh]  #7 -> [pwsh]  #8 -> [pwsh, read]
#9 -> [pwsh, read]  ... #13 -> [grep, pwsh]  #14 -> [pwsh]
```

也就是说：模型把“继续。”理解成“去干活”，于是用 `pwsh`/`read`/`glob`/`grep` **翻我们真实仓库**。这是宿主里正常的 agent 行为，不是记忆插件的 bug——我最初把它归因成“反复 `ctx_find`”，逐条报文推翻了它。

真正要改的是**实验设计**：记忆测试的 setup 轮不该让 agent 有活可干。

- 熔断按任务归属（`aborted: [{step:'setup'|'question', reason, ms}]`），能直接看出是哪一步失控；
- `question` 步 **0/10** 触发 → 提问轮本身是稳的，浪费都发生在 setup；
- 这也解释了 A-5b 那次 43 请求：同样是 cwd 指向真实仓库后，agent 开始自己找活干。

## 5. 仍未解决

1. **setup 轮会让 agent 去逛工作区**（3/10，已定性为实验设计问题）：测试用的 cwd 是真实仓库，模型看到“继续。”就去 `pwsh`/`read`/`glob`。修法是换一个**空工作区**或给 setup 轮加一条“不要动文件”的约束，再重跑，否则这 3 轮的费用（¥0.036/¥0.018）会污染成本口径。
2. 两个场景的**失败率为 0** 只说明这两条夹具稳，不代表别的问法稳（否定/指代/跨压缩各只测过 3–10 次）。
3. 判分仍是“必须给独立值”，对“先否定后纠正”的回答一律判负（A-5 REFERENCE r2 的类型），没做人工复核通道。
4. 相对时间的合法换算仍会被日期闸门误删（A-8）。
