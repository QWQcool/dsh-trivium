## 二、Super-agent 是什么（以开源原型为准）

DeepSeek Harness 团队 2026-10-31 公开，原型仓库 `deepseek-ai/dsh-superagent-prototype`（MIT，研究代码，
README 明确声明"**与文章描述的实现并不一致**，文中部分设计只是未来方向"）。

五个结构性概念：

1. **Router / Worker 双层**：Router 常驻，接多渠道消息、维护全局上下文、分派任务；Worker 各自独立会话与目录并发执行，可再调 Subagent。
2. **事件驱动两级过滤**：程序层快筛 + 语义层慢判；订阅与直通。
3. **Inline & Spill 上下文组织**：热上下文内联、冷上下文外置（文章未给阈值）。
4. **存算分离（脑手分离）**：推理决策与执行/状态解耦。
5. **外部 Watchdog**：超时、卡死、异常自愈。

原型里可直接观察到的形态：Source 事件 → work item → **独立 session + 独立目录**执行 → **回报原会话**；
"Source" 是官方承认的扩展点；行动准则是"被请求，或团队写好的规则允许"。

## 三、若 DSH 上 Super-agent，我们要开工什么

我们的插件现在是**单工作区、单写者、会话内事件驱动**，与上面的结构有四处硬冲突：

| 冲突 | 现在 | Super-agent 下 | 要做什么 |
|---|---|---|---|
| **作用域** | 记忆边界 = `cwd/.dsh/trivium.tdb` | 每个 work item 一个独立目录，记忆会散落在各 work item 里 | 引入"上层作用域"（仓库/团队级）+ 继承与回流：Worker 读上级、写回上级 |
| **并发** | 单写者锁，第二个进程 `lock-busy` 跳过本轮 | Router 会并行开多个 Worker，锁冲突会成为常态 | 改成"集中写"（Router 侧单点写）或支持多写者安全追加 |
| **事件源** | 只吃 `user/message`、`tool/*`、`turn/end` | 事件来自 GitHub/飞书等 Source，不是会话消息 | 加 Source 适配层 + 事件去重 + 非会话事实的写入路径 |
| **跨会话决议** | 去重按"同一事件（messageId/seq）" | 同一决策会在多个 work item 里各写一份（事件不同） | 去重键要从"事件"升级到"事实身份"（这正是方向 3 的向量相似） |

另外两处需要重新评估的既有假设：

- **重放 8 秒上限 / 锁 30 秒 TTL**：长驻多 Worker 下要重新定标；
- **面板形态**：Super-agent 有"需要人处理"的面板，我们的"待确认替代/恢复中/待处理记忆"可以直接挂上去——
  这也是为什么 **P/P′ 与 Super-agent 天然契合**：它本来就有授权与人工验收的位置。

**建议的开工顺序**：先做"作用域继承"的最小验证（Worker 目录 → 上级库只读 + 写回），
再决定并发模型（集中写 vs 多写者）。不要在原型 API 稳定前做深度耦合——它的 README 自己说了，
文章里的设计可能还没实现。

## 四、可以直接借鉴到本插件的

| 借鉴 | 我们现在的做法 | 可以怎么改 |
|---|---|---|
| **两级过滤** | 有内容门（`shouldExtractBatch`），但"语义判断"只在可疑空回答时用过一次 | 统一成"程序快筛 → 一次语义慢判"，减少无效模型调用 |
| **Inline & Spill** | 短地图是 Inline，历史全在库里（Spill），但没有热度策略 | 地图按"最近被引用/最近变化"排序，冷事实留给 `ctx_read` |
| **订阅直通（省 37% token）** | 每次会话启动重建并全量注入地图 | 改成增量注入：地图带版本号，只有变化部分进提示词 |
| **存算分离** | 已是 trivium.tdb + 旁路 JSON | 进一步把"抽取（推理）"与"状态"解耦，便于多 Worker 共享一份记忆 |
| **Watchdog** | 有 8s 重放上限、30s 锁 TTL、心跳 | 加"卡住检测 + 自愈"：抽取卡死时记录并按 work item 重启重放 |
| **授权模型** | 无（自动建边） | 正是 P/P′ 的确认流程，可参考它的"只做被授权的事"准则 |

其中 **增量注入** 与 **地图热度** 是零依赖、当天可验证的两条，建议优先。

## 五、借鉴项开工单（已并入后续开发方向）

六条都已写成可验收的工单，**不依赖 Super-agent 上线**，现在就能做。
排序依据：能否单独验证 → 收益 → 是否给适配铺路。

### B1 事件两级过滤（P1，1 日）

- **现状**：`shouldExtractBatch` 是程序层内容门；"语义慢判"只在"可疑空回答"时用过一次。
- **改法**：新增 `screenEvent(text) → 0|1|2`（规则打分：0 无信息、1 可能有、2 明确有事实）。
  0 分不进窗口、不花钱；1 分走现有抽取；2 分进 batch 前排。**不新增模型调用**，
  "慢判"仍复用抽取调用本身，避免为了省 token 反而多花钱。
- **验收**：同一批夹具下模型调用数下降 ≥20%，抽取命中不下降（离线桩 + A5 夹具）。
- **风险**：0 分误判会漏抽 → 只有命中完整白名单（寒暄/纯工具指令）才给 0 分，规则可审计。

### B2 地图热度（P1，1–2 日）

- **现状**：`buildShortMapReport` 按类型与更新时间排，没有"被用过"的信息。
- **改法**：`ctx_read` / `ctx_find` 命中时更新 `lastUsedAt`（节流 60s 写一次旁路 JSON），
  地图按 `(引用次数, 最近使用, 更新时间)` 降序；冷事实留给 `ctx_read`。
- **验收**：构造 50 条事实、只问过其中 3 条，重建地图后 3 条必须在 400 token 内；
  同一夹具的 token 数不上升。
- **风险**：写盘频率 → 节流 + 只写旁路，不进主库事务。

### B3 增量地图注入（P1，1–2 日）

- **现状**：每次会话启动重建地图并全量写进提示词。
- **改法**：地图带 `mapVersion`（事实集合指纹 + 预算）；会话内记录上次注入版本，
  未变化则**不重复注入**；变化时注入"变更摘要 + 差异行"。
- **验收**：连续 3 轮无新事实的会话，注入 token 下降 ≥50%，回答正确率不降。
- **约束**：四工具不动，所以模型必须仍能用 `ctx_find`/`ctx_read` 补全；
  首轮、以及"距上次注入超过 N 轮"必须全量注入，避免模型失去全局观。
- **风险**：模型漏看差异 → 用"摘要行 + 计数"保证它知道还有哪些没展开。

### B4 抽取与状态解耦（P2，2 日，为适配预付）

- **现状**：`distill` 直接在进程内开库写。
- **改法**：抽一层 `MemoryWriter` 接口（当前=进程内实现），写路径只依赖接口。
- **验收**：把实现换成桩后，`p63`/`p65`/`p69` 仍通过。
- **收益**：Super-agent 的 Router 单点写可以直接换实现，不用改业务代码。
- **说明**：当前没有直接收益，属于预付成本。

### B5 卡住检测与自愈（P2，1 日）

- **现状**：有 8s 重放上限、30s 锁 TTL，但卡住只打一条 warn。
- **改法**：把"抽取超时 / 锁未释放超 TTL / 重放超预算"记成 `stuck` 事件进 status 与变更记录；
  下次会话启动清理 stale 锁（已有）并重放 pending（已有），补一条"已自愈"记录。
- **验收**：桩让抽取卡 30 秒，status 出现 `stuck`，下一轮正常抽取且记录 `recovered`。
- **风险**：日志噪声 → 每类事件每会话只记一次。

### B6 授权模型（= P/P′，另见 `SUPERSEDE-CONTRACT-OPTIONS.md`）

- 不属于本条，交叉引用：Super-agent 的"只做被请求或规则允许的事"就是 P/P′ 的确认流程。

## 六、Super-agent 上 DSH 的适配计划（先列，等它上线再做）

### 触发条件（满足任一即启动阶段 1）

1. DSH 发布带 Router/Worker 的 profile 或 bundle；
2. `dsh-superagent-prototype` 从"单 commit 快照"变成持续迭代，且 `docs/007-architecture.md` 给出插件接口；
3. DSH 出现 `Source` 类插件或 `work item` 概念。

### 阶段 0：现在就能做（与 Super-agent 解耦）

- B1 / B2 / B3 / B5 四项（见第五节）；
- **作用域抽象**：把 `store` 的 `cwd` 参数抽象为 `scope`（`workspace` / `parent` / `inherit`），
  只加参数不改行为，为阶段 1 铺路。
- 验收：现网行为零变化，`run-all` 全绿。

### 阶段 1：作用域与并发（触发后 1–2 周）

- Worker 目录 → 读上级库（只读继承）+ 写回上级（走 Router 单点或带锁追加）；
- 并发模型二选一：**集中写**（推荐，B4 打底）或**多写者安全追加**（需要引擎支持）；
- 重新定标：重放等待预算（现 8s）、锁 TTL（现 30s）在多 Worker 下的取值；
- 验收：三个 Worker 并行处理同一仓库，事实不重复、不丢、短地图不串味。

### 阶段 2：事件源与跨会话去重

- `Source` 适配层（GitHub/飞书事件 → `turns`），复用现有内容门与凭据/日期闸门；
- 去重键从"事件（messageId/seq）"升级到"事实身份"（向量相似 + 名称族），即方向 3；
- 验收：同一 issue 的讨论与对应 work item 的结论不产生两条互相矛盾的决策。

### 阶段 3：面板与提案

- 把"待确认替代 / 恢复中 / 待处理记忆"接入它的"需要人处理"面板；
- 若届时已选 P/P′，确认动作走该面板，而不是我们自己的设置页。

### 回滚与隔离

每一阶段都必须能退回"单工作区单写者"模式：用一个开关（默认关）控制作用域继承与多写者，
开关关闭时行为与 0.8.3 完全一致。
