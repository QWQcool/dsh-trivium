# 后续方向，以及 Super-agent 架构的适配与借鉴

日期：2026-11-02。对象：dsh-trivium 0.8.3（已发布）之后。

## 一、除 P / P′ 之外的方向

按"能不能独立做完、收益多大"排序。P/P′ 见 `SUPERSEDE-CONTRACT-OPTIONS.md`。

| # | 方向 | 现状 | 工作量 | 收益 |
|---|---|---|---|---|
| 1 | **HTTP 级自动回归** | `p69` 只覆盖存储层；`/status` 的 `emptyAnswer`、凭据不回显只由复验方脚本验证 | 半日 | 把"已修"变成"可回归" |
| 2 | **零请求空回答** | W9 真机出现过一轮提问**没有任何模型请求**，至今未复现 | 1–2 日 | 关掉最后一个"整轮无输出"的未知 |
| 3 | **语义去重（同义不同文）** | 精确同文/同名已折叠；改名或改措辞仍留两条。bigram 相似度实测**反向**（真重复 0.26 / 不同事实 0.44），不可用 | 2–3 日 | 减少重复节点；需改用向量相似（库里已有 embedding 队列） |
| 4 | **锁的覆盖面与粒度** | 只保护自动抽取写入；`ctx_remember`、文件导入仍可能撞"已被打开"。锁粒度是整轮（含模型调用） | 1–2 日 | 并发下不再整轮跳过 |
| 5 | **日期与时间** | 只认 `YYYY-M-D` 三写法；不认美式/英文月份/中文数字；时区硬编码 `Asia/Shanghai`；`月底/尽快` 不解析 | 1 日 | 覆盖更多真实说法 |
| 6 | **短地图预算与热度** | 每次会话启动重建、全量注入；`400 token` 预算无优先级 | 1–2 日 | 直接省 token，且更不容易被噪声挤掉关键事实 |
| 7 | **内核升级** | pin `triviumdb@0.9.0-beta.3` | 等 0.9.0 稳定 | 避免长时间落后 |
| 8 | **B 站 E1-B** | 依赖对方扩展点 | 我方无法单独完成 | 暂缓 |

## 二、Super-agent 是什么（以开源原型为准）

DeepSeek Harness 团队 2026-10-31 公开，原型仓库 `deepseek-ai/dsh-superagent-prototype`（MIT，研究代码，
README 明确声明"**与文章描述的实现并不一致**，文中部分设计只是未来方向"）。

五个结构性概念：

1. **Router / Worker 双层**：Router 常驻，接多渠道消息、维护全局上下文、分派任务；Worker 各自独立会话与目录并发执行，可再调 Subagent。
2. **事件驱动两级过滤**：程序层快筛 + 语义层慢判；订阅与直通。
3. **Inline & Spill 上下文组织**：热上下文内联、冷上下文外置（文章未给阈值）。
4. **存算分离（脑手分离）**：推理决策与执行/状态解耦。
5. **外部 Watchdog**：超时、卡死、异常自愈。

原型里可直接观察到的形态：Source 事件 → work item → **独立 session + 独立目录**执行 → **回报原会话**；
"Source" 是官方承认的扩展点；行动准则是"被请求，或团队写好的规则允许"。

## 三、若 DSH 上 Super-agent，我们要开工什么

我们的插件现在是**单工作区、单写者、会话内事件驱动**，与上面的结构有四处硬冲突：

| 冲突 | 现在 | Super-agent 下 | 要做什么 |
|---|---|---|---|
| **作用域** | 记忆边界 = `cwd/.dsh/trivium.tdb` | 每个 work item 一个独立目录，记忆会散落在各 work item 里 | 引入"上层作用域"（仓库/团队级）+ 继承与回流：Worker 读上级、写回上级 |
| **并发** | 单写者锁，第二个进程 `lock-busy` 跳过本轮 | Router 会并行开多个 Worker，锁冲突会成为常态 | 改成"集中写"（Router 侧单点写）或支持多写者安全追加 |
| **事件源** | 只吃 `user/message`、`tool/*`、`turn/end` | 事件来自 GitHub/飞书等 Source，不是会话消息 | 加 Source 适配层 + 事件去重 + 非会话事实的写入路径 |
| **跨会话决议** | 去重按"同一事件（messageId/seq）" | 同一决策会在多个 work item 里各写一份（事件不同） | 去重键要从"事件"升级到"事实身份"（这正是方向 3 的向量相似） |

另外两处需要重新评估的既有假设：

- **重放 8 秒上限 / 锁 30 秒 TTL**：长驻多 Worker 下要重新定标；
- **面板形态**：Super-agent 有"需要人处理"的面板，我们的"待确认替代/恢复中/待处理记忆"可以直接挂上去——
  这也是为什么 **P/P′ 与 Super-agent 天然契合**：它本来就有授权与人工验收的位置。

**建议的开工顺序**：先做"作用域继承"的最小验证（Worker 目录 → 上级库只读 + 写回），
再决定并发模型（集中写 vs 多写者）。不要在原型 API 稳定前做深度耦合——它的 README 自己说了，
文章里的设计可能还没实现。

## 四、可以直接借鉴到本插件的

| 借鉴 | 我们现在的做法 | 可以怎么改 |
|---|---|---|
| **两级过滤** | 有内容门（`shouldExtractBatch`），但"语义判断"只在可疑空回答时用过一次 | 统一成"程序快筛 → 一次语义慢判"，减少无效模型调用 |
| **Inline & Spill** | 短地图是 Inline，历史全在库里（Spill），但没有热度策略 | 地图按"最近被引用/最近变化"排序，冷事实留给 `ctx_read` |
| **订阅直通（省 37% token）** | 每次会话启动重建并全量注入地图 | 改成增量注入：地图带版本号，只有变化部分进提示词 |
| **存算分离** | 已是 trivium.tdb + 旁路 JSON | 进一步把"抽取（推理）"与"状态"解耦，便于多 Worker 共享一份记忆 |
| **Watchdog** | 有 8s 重放上限、30s 锁 TTL、心跳 | 加"卡住检测 + 自愈"：抽取卡死时记录并按 work item 重启重放 |
| **授权模型** | 无（自动建边） | 正是 P/P′ 的确认流程，可参考它的"只做被授权的事"准则 |

其中 **增量注入** 与 **地图热度** 是零依赖、当天可验证的两条，建议优先。
