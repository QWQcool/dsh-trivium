# W11 证据：空回答的人工复现与可见性

基线 `074cc60`。零模型费用（本地桩）。

## 1. 人工复现（已成功）

脚本 `.tmp/empty/repro.mjs`：桩对**提问轮**返回空文本（`text: ""`），其余照常。

```text
setup    exit=0  final="收到。"
before question: nodes=0 []
question exit=0  requests=4  final=""
stdout: {"type":"text","text":""} → step_end → turn_end reason="completed" → {"type":"final","text":""}
```

由此可以确定三件事：

1. **提问轮确实发出了请求**（4 个），不是"没请求"；
2. 宿主把**空文本当成正常完成**（`turn_end: completed`、退出码 0）；
3. 插件的 pre-step 没有参与，也没有报错。

## 2. 与 W9 r2 的区别（必须说清）

| | W9 r2（真机） | 本次人工复现 |
|---|---|---|
| 提问轮请求数 | **0** | 4 |
| final | 空 | 空 |
| 结论 | 未知，无报文 | 模型返回空文本，宿主照常完成 |

**两者不同源**。人工复现证明"空 final"可以由模型返回空文本造成，但**不能**解释 r2 的"零请求"。
r2 那种情况仍然没有复现，需要等下一次真机出现（采集脚本已经会保存提问轮 stdout/stderr 与请求数）。

## 3. 这一轮改了什么（可见性，不是修复）

`lib/index.js` 新增：

- `isEmptyAssistantAnswer(event)`：区分"空回答"与"只调工具的步骤"——
  工具步骤不算空；空 content、空 text 块、纯空白算空；
- 命中时在 `status.emptyAnswer` 记一条 `{ at, sessionId, seq, count }`，让长驻宿主里
  "这次回答是空的"能直接看到，而不是只能翻报文。

**没有做的事（也不该由插件做）**：替宿主重试模型调用。空回答的修复点在宿主的 turn 循环
（`dsh-llm-retry` 目前不重试空文本），插件拿不到那个控制权。

`p68` **6/6**：空 content / 空 text / 纯空白都算空；有文本不算；只有工具调用不算；
工具调用带一个空 text 块也不算。

## 4. 影响评估（重要）

W9 r2 里事实是**已经写进库的**（2 个节点），丢的只是这一轮的话。
所以空回答属于"体验缺陷"，**不是记忆丢失**，优先级低于此前修掉的那些。

## 5. 仍未解决

1. r2 那种"零请求"没有复现，也没有找到成因。
2. `status.emptyAnswer` 只在长驻宿主里可见；headless 一次性进程退出后看不到，本轮**没有**做端到端验证
   （只在单测层面验证了分类逻辑）。
3. 宿主侧若要真正兜底，需要"空文本 → 重试一次"的策略，属于宿主配置/插件之外。
