# W6 证据：单写者（F-W05 方案 A）

基线 `c9b6e23`。零模型调用、零费用。

## 先更正 W5 的一个结论

W5 当时把 `copies=2` 归因为"两个进程各写一份"。逐层追下去，**这个归因是错的**：

- 引擎（原生 `triviumdb` 扩展）本身**拒绝**第二个写者。p55 直接复现了原始报错：

  ```text
  m.tdb' is already opened with an incompatible access mode
  code: 'GenericFailure'
  ```

  也就是说 W5 里那个 `exit=1` 是**引擎拒绝打开**，不是插件重复写。
- 那两份节点来自**同一进程**：规则层为同一句话写了自己的候选，模型候选再写一份（两条路径都在 0.8.2 里存在，与本批无关）。
- W5 的桩当时对**任何**抽取提示都返回同一候选，进一步放大了这个假象。

所以：**并发写重复事实是我们的误判；真实问题是"第二个进程直接崩掉"。**

## 本片解决的问题

崩溃变成"跳过 + 可见"：

| 之前 | 现在 |
|---|---|
| 第二个进程 `openWorkspaceDb` 抛错、进程 exit 1，用户只看到报错 | 第二个进程拿不到锁就**不打开库**，本轮不抽取、pending 保留、审计记一条 `lock-busy`，下一个事件继续 |
| 谁也不知道发生过 | `lastExtract.skippedBy = 'lock-busy'` + 变更记录 + 一条 warn |

**顺序是关键的**：锁必须在 `openWorkspaceDb` **之前**拿。p55 最初把锁放在 distill 里（开库之后），第二个进程照样崩在开库上——这是本轮唯一一次真实的实现返工。

## 断言

`p54` 17/17（锁原语）：先到先得、第二个不等待直接 busy、释放幂等、TTL 接管残锁、新鲜锁不被抢、**释放时校验 nonce 不会误删别人的锁**、审计标签存在、残锁最终可回收。

`p55` 8/8（两个真进程）：一个写、另一个 `locked`、两个进程都正常退出、事实可读、后续进程不被残留锁阻塞、结束后无锁文件。

全量 `run-all` → **56/56 passed**。

## 仍然存在的边界

1. **只覆盖抽取写入**。`ctx_remember` 工具、文件导入走的是别的入口，仍然可能在并发下撞到引擎的"已打开"错误（不会重复写，但会失败）。要不要把锁推到这些入口，是下一步的决定。
2. **引擎的锁语义仍不可见**：它是原生扩展，我们只能依赖它自己的报错行为，不能保证未来版本不变。
3. **锁粒度是整轮抽取**（含模型调用），所以并发时第二个会话是"整轮跳过"，不是"等 200ms 再写"。这是方案 A 的有意取舍。
4. **崩溃恢复靠 TTL（30 秒）**：进程被 kill 后，下一位最多等 30 秒才接管；期间那些窗口都会记 `lock-busy`。
