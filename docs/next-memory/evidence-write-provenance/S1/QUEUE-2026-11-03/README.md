# Router 队列深度与延迟实测（2026-11-03）

基线 `main` @ `4c0fb3d`。零模型调用、零费用；只在本机临时工作区与命名管道上跑。
复现：`node scripts/bench-router-queue.mjs`（默认 2/5/10 个 Worker × 每个 50 次写）。

## 问题

Router 解决了"写不丢"，但没回答"排多久"。排队延迟决定它能不能直接接进宿主，
也决定要不要加背压（拒绝超出深度的请求）。

## 结果

| Worker | 每 Worker 写 | 总写 | 落库 | p50 | p95 | p99 | maxQueue | 墙钟 | 吞吐 |
|---|---|---|---|---|---|---|---|---|---|
| 2 | 50 | 100 | 100 | 8.4 s | 8.4 s | 8.4 s | 50 | 8.5 s | 11.8 /s |
| 5 | 50 | 250 | 250 | 24.1 s | 24.1 s | 24.1 s | 50 | 24.2 s | 10.3 /s |
| 10 | 50 | 500 | 500 | 50.4 s | **75.3 s** | 75.3 s | 50 | 76.1 s | 6.6 /s |

**一条都没丢**（落库 = 总写），但 10 个 Worker 同时打 50 条时，p95 是 **75 秒**。

## 根因：不是队列，是每次写都 flush

单独测同一个库的直接写（不经过 Router）：

```
insert 20 : 187.6 ms each
flush ×20 : 1824 ms total, 91.2 ms each
```

`insertNode` 里有 `persist()` → `db.flush()`，而一次 flush 在这台机器上约 **91 ms**；
插入一次约 **188 ms**（flush + 索引更新 + sidecar 调度）。

于是：

- 单工作区的写吞吐上限 ≈ `1 / 0.188s` ≈ **5 次/秒**，与 Worker 数量无关；
- 队列里 500 条 → 尾部必然等近百秒；
- Router 本身**没有增加**额外开销（2 个 Worker 时每条约 84 ms，与直接写同量级）。

这也修正了上一片（`S1/CONCURRENCY`）的一个解释：那里"50 ms 抽取也撞锁 19.4%"，
不只是模型延迟，**锁的持有时间里还包含一次约 190 ms 的插入**。

## 结论

1. **背压不是解**。拒绝请求只会把"排队"换成"失败"，而每次写仍然要付 190 ms。
2. **批处理才是解**：Router 持有唯一句柄，完全可以把一个时间窗内的 K 条写合并成一次 flush。
3. **在批处理落地前，Router 不应该接进宿主**：任何一个 Worker 突发 50 条就会把 p95 拖到分钟级。
4. 队列深度本身很小（maxQueued = 50，等于并发客户端数 × 每客户端突发），
   说明瓶颈不是队列管理，而是每一跳的落盘成本。

## 修复后（同一天，批处理已落地）

`lib/store.js` 新增 `runDeferredWrites(db, fn)` 与 `flushWorkspaceDb(db)`：
批窗口内的所有变更都跳过 `persist`，整批结束时付**一次** flush；
`lib/router.js` 改成"每个事件循环 tick 一批"——先批量应用，再 flush，**flush 之后才回包**（回包仍然代表已落盘）。

同一份基准、同一台机器：

| Worker | 总写 | 落库 | p95（前） | p95（后） | 吞吐（前） | 吞吐（后） |
|---|---|---|---|---|---|---|
| 2 | 100 | 100 | 8 437 ms | **126 ms** | 11.8 /s | **518 /s** |
| 5 | 250 | 250 | 24 114 ms | **165 ms** | 10.3 /s | **1 025 /s** |
| 10 | 500 | 500 | 75 270 ms | **206 ms** | 6.6 /s | **1 462 /s** |

p95 降了 50–400 倍，吞吐升了 40–220 倍，落库仍是 500/500。深度队列（200）不再意味着分钟级等待。

`smoke-p81` 增加两条：20 次并发写只产生 ≤5 次 flush（前 20 次），且 20 条都在库里。


## 验收

```
node scripts/smoke-p81.mjs   → 13/13（新增：突发后 queued 归零、maxQueued ≥ 1、applied 计数、failed 为 0）
node scripts/run-all.mjs     → 82/82
```

`lib/router.js` 新增 `stats()`（`applied / failed / queued / maxQueued / uptimeMs`），
刻意不加查询接口——查询自己也会排进队列。

## 未覆盖 / 已知边界

1. **批处理没有实现**：本片只测，不做。`insertMany` 或"延迟 flush + 批量提交"是下一步。
2. **只有一台机器、一块盘**：91 ms/flush 是这台 Windows 机器的数；SSD 与机械盘差异很大，换机需重测。
3. **flush 的构成没有拆开**：不知道 91 ms 里有多少是 fsync、多少是索引重建。
4. **没有测背压策略**（超深度拒绝、超时拒绝）的实际收益。
5. **队列不分优先级**：一次大批量与一条关键更正排同一个队。
6. **只有单工作区**：多 Router 并发写不同库时的总吞吐未测。
