# 阶段 1 前置：多写者锁竞争实测（2026-11-03）

基线 `main` @ `12fa797`。**不改产品代码、不调模型、不碰 `~/.dsh`**，只跑本机三个子进程。
可复现命令：`node scripts/bench-lock-contention.mjs 3 12`。

## 为什么测这个

阶段 1 要在两个方案里选一个：**集中写**（一个 Router 代表所有 Worker 落库）还是
**多写者安全追加**（各写各的，靠锁）。在做决定前，先得知道今天的锁在"多 Worker 同时抽取"
下到底会撞多少次、撞了会不会丢事实。

## 怎么测

三个子进程指向同一个临时工作区，每个进程每轮：

```
withWorkspaceLock(cwd, async () => { openWorkspaceDb(cwd); insertNode(...); sleep(workMs); })
→ closeAll()（每轮释放句柄）
```

`workMs` 模拟抽取耗时（桩模型 50 ms / 中等 400 ms / 真实模型调用约 1500 ms），
两轮之间隔 `gap`（基准 800 ms，带随机抖动，避免三个进程同步起跑造成的相位锁定）。
工作区在 `mkdtempSync` 下，跑完删除。

## 结果

| 场景 | 尝试 | 成功 | 撞锁 | 撞锁率 | 落库事实 | 丢写 | 墙钟 |
|---|---|---|---|---|---|---|---|
| 快速抽取（50 ms） | 36 | 29 | 7 | **19.4%** | 29 | **0** | 12.7 s |
| 中等抽取（400 ms） | 36 | 17 | 19 | **52.8%** | 17 | **0** | 16.0 s |
| 真实模型级抽取（1500 ms） | 36 | 8 | 28 | **77.8%** | 8 | **0** | 16.7 s |

撞锁率随 `work / gap` 单调上升，符合"重叠概率"而不是随机噪声：
三个 Worker、800 ms 一轮、单次抽取 1.5 s 时，**约 78% 的抽取抢不到锁**。

## 三个结论

1. **锁本身没丢写**：每个成功尝试都落了一条事实（落库数 = 成功数，三档都是 0 丢写）。
   输的一方走的是"窗口留 pending、下个事件再试"，不是丢弃。
2. **撞锁不是罕见事件**：真实模型延迟下 3 个 Worker 就有 78% 的抽取被推迟。
   这不是"要不要加锁"的问题，是多 Worker 形态下的常态。
3. **真正危险的不是锁，是"推迟"落在了一个不会再被打开的目录上**。
   本基准里每个 Worker 都持续循环，所以推迟总能补上；Super-agent 的 work item 目录是短命的——
   item 结束、目录再没人开，pending 窗口就永远躺在那儿。**事实不是被锁丢的，是被"没有人再来开这个库"丢的。**

## 另一个现场：句柄比文件锁更硬

第一版基准里 Worker 每轮不关库，第二个进程直接失败：

```
TDB_ERROR: 数据库已锁定 (Database locked): ... is already opened with an incompatible access mode
```

插件当前按进程缓存 `openWorkspaceDb`，所以**一个进程只要开过，库就对这个进程之后的整个生命周期保持打开**，
文件锁（`trivium-write.lock`，30 s TTL）在这之后形同虚设。这与 2026-11-03 真机里看到的
`the workspace memory DB is locked by another DSH instance` 是同一件事。

## 对阶段 1 的含义

| 方案 | 今天的数据怎么说 |
|---|---|
| **多写者 + 锁（现状）** | 不丢写，但有 78% 的抽取被推迟；推迟的存活依赖"这个库还会被再次打开"，与 work item 目录模型直接冲突 |
| **集中写（Router）** | 冲突不会消失，只会变成排队：串行化后总吞吐上限是 `1 / work`，3 个 Worker 也就 0.67 次/秒。好处是"推迟"变成"保证送达"，代价是 Router 必须活得比任何一个 Worker 长 |
| **多写者安全追加** | 需要引擎支持多写者；当前 `triviumdb` 明确拒绝，不在我们手里 |

由此，阶段 1 的判定条件可以写死：

- 若 Worker 目录是**短命**的（跑完即弃）→ **必须集中写**，否则推迟等于丢；
- 若 Worker 复用固定目录、并且会话会重启 → 现状的"推迟"可接受，只需把 pending 的可见性做出来；
- 两条都需要 Router 存在，所以 **Router 是阶段 1 的前置，而不是可选优化**。

## 没测到的

1. **没有真 Router**：基准里三个进程自己抢锁，没有一个中央写者，所以"排队延迟"只有理论值。
2. **没有真模型**：`workMs` 是睡眠，真实抽取的分布（含长尾）未测。
3. **没测等待型锁**：现实现是不等待；"等待 200 ms 再放弃"这类折中方案的收益未量化。
4. **只在 Windows 本机**：文件锁语义在 Linux/macOS 上未复核。
5. **`gap=800ms` 是假设值**：真实 work item 的事件间隔可能大得多，届时撞锁率会显著下降。
