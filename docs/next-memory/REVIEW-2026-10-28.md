## 阻止0.5.0发布的三个问题

### P1 同一轮累计预算未记账

位置：`lib/turn-ledger.js:118`、`lib/turn-ledger.js:135`、`lib/index.js:686`附近；配套检查 `lib/context-budget.js` 的返回记录。

`selectContextRecords()`只计算plan总tokens，没有给每条record设置tokens。运行时调用 `reserve(sessionId, turnKey, plan.records)`，reserve把未定义的 `r.tokens` 当0，commit累计的spent也就一直是0。

独立复现：三个已钉选长条目，完全相同的用户轮、完全相同的候选集，连续三个pre-step规划分别投递一条。每次217估算token，合计651；每次commit后账本spent仍为0，下一步又得到完整300额度。单条已投递指纹去重有效，但之前被预算挤出的条目会在后续步骤继续获得新预算。

修复要求：对实际渲染后的总成本记账，包括两个消息块的标题/包装；不要靠手工在测试夹具里塞record.tokens掩盖接线缺失。commit必须幂等，reserve/rollback失败不能扣费，budget=0不能回落成300。新增“同候选集多步骤、首步有预算淘汰项”的运行时回归，断言累计≤300。

### P1 新版本id配上旧版本正文

位置：`lib/context-budget.js:262`，`lib/revisions.js:80`，`lib/index.js:351`。

当前版本解析只返回currentId/archived/stale。规划器把record.id换成后继id，却保留原候选的l0、期限和path。因此自动召回/只读预览会把旧事实包装成“当前版本”。

独立复现：#2正文为“CookieLegacy 是旧鉴权方案。”，#3正文为“HeaderCurrent 是新的唯一鉴权方案。”；确认#3替代#2后查询CookieLegacy，预览输出：

```text
[decision#3 matched_history=#2 → current=#3] CookieLegacy 是旧鉴权方案。
```

这比“查不到”更危险：模型看到的是新id，但读到的是已被替代的指令。主动 `ctx_find` 另有重新读取新payload的分支，因此不能只用工具调用测试代替自动召回测试。

修复要求：归一时读取并重新投影当前节点的正文、类型、期限、路径和卫生/可用性状态；保留旧id只用于命中来源指针。实际自动注入、预览和ctx_find共用一个正确的归一逻辑。测试必须断言新正文出现、旧正文不冒充新版本，不能只断言id变了。

### P1 导入的版本节点被正文去重合并，形成自环

位置：`lib/store.js:827`、`lib/store.js:856`、`lib/store.js:877`；JSONL的对应导入路径也需一并核对。

导入先按导出id检查关系结构，真正写入时又按文本包含关系查找合并目标。两个URI不同、属于不同版本的节点，只要新正文包含旧正文，就会映射到同一个本地id。后续没有重新验证映射后的关系，直接提交 `id --supersedes--> id`。

独立复现：URI分别为rev100/rev200，正文分别为“鉴权统一使用请求头携带会话凭据。”与该句加“所有请求还必须校验签名。”，导入正常的200→100关系。返回 `ok:true, created:1, merged:1, revisionLinked:1`；实际只剩一条决策，其supersedes指向自己，`currentHeadOf()`返回cycle，原版本正文和URI身份丢失。

修复要求：明确URI身份优先；不同稳定URI的版本节点不能因为正文相近而合并。写入前规划一对一映射，验证映射后的关系及与现库组合后的完整拓扑，再提交；不能等正文已经覆盖才发现冲突。补充文本包含、完全相同正文但不同URI、与现库拼接产生环、事务失败的回归。事务失败后留下已写节点并仍返回ok:true的路径，也不符合本次导入失败不半提交的验收要求。
