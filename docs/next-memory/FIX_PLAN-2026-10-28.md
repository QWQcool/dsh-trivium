## 3. R1 统一当前版本投影

涉及：`lib/revisions.js`、`lib/context-budget.js`、`lib/index.js`、`lib/recall-preview.js`、`lib/tools.js`、必要的store投影辅助函数。

### 设计

建立一个共用的版本归一入口，例如 `resolveRecallRecord(db, candidate, options)`。可以调整命名，但自动注入、只读预览、ctx_find必须使用一致的当前事实投影，不再各自换id。

输出必须来自同一个有效节点：`id / type / l0 / until / stale / archived / dirty / path`。版本解析返回原始payload或完整受控投影均可；不得只返回currentId后保留旧l0。新节点读取失败、链循环、超限或状态不允许时，返回明确的丢弃原因，不把旧正文装进新id兜底。

旧id仅作为 `matchedHistory` 证据指针保存。path须来自当前节点，或明确为空；不能把旧路径冒充当前关系。归一、去重之后再决定最终预算与返回条数。

三种使用目的要分开：

- **automatic**：只输出当前、未归档、未过期且通过卫生检查的事实。
- **explicit find**：保留0.4.22的 `include_stale` 期限语义；允许时可返回带stale标记的当前头，不复活其旧前驱。
- **manual pin / ctx_read**：用户明确钉选历史节点时保留其原id与正文并标历史；ctx_read(oldId)继续读oldId。不要为复用代码悄悄把人工历史读取换成新版本。

### 验收

- CookieLegacy查询能映射到HeaderCurrent，输出同时断言“新id+新正文”，旧正文只允许出现在显式历史读取中。
- 当前节点的期限、卫生、归档状态改变后，自动召回不输出失效链；不得沿用旧状态。
- 同时命中新旧两个版本时，自动结果只有一条当前事实；指针保留真实旧命中。
- 预览结果与实际pre-step采用同一候选fixture时，正文/状态/预算一致。
- 人工旧pin仍是旧正文且带历史标记；ctx_find与ctx_read原有契约不被破坏。

## 4. R2 实际记账、用户轮与累计预算

涉及：`lib/context-budget.js`、`lib/turn-ledger.js`、`lib/index.js`、`scripts/verify-package.mjs`。

### 记账方案

优先按**本次实际渲染总量**建立reservation，例如 `reserve(session, turn, {records, totalTokens, correctionIds})`：

1. 选择结构化记录，渲染最终pins和recall消息。
2. 使用同一 `estimateTokens()` 计算实际要发送的两个完整消息块，包含标题、标记、路径与换行。
3. reservation保存这次totalTokens；commit只给spent加一次该总量，并记录相应指纹。
4. 单条record的tokens如果UI需要，可以按前缀边际成本派生，但不作为另一个可能漏接的账本真相。

RESULT提出的“按前缀差值给record.tokens”也可接受，但必须证明 `sum(record.tokens) === rendered.total`，并用真实runtime调用验证。无论选哪种实现，都不能继续把缺失tokens默认为成功的0成本投递。

### 状态规则

- budget未提供时使用默认值；显式0必须返回空计划。非法或负数预算按统一验证策略拒绝/归零，不得恢复成300。
- `commit()`对已提交reservation直接返回，不重复计费；rollback只取消未提交reservation。旧turn或旧generation的reservation不得写入新账本。
- 在存在异步检索或两个在途pre-step时，reserve/commit必须防止共同消费同一份剩余额度。重新核对账本、必要时重规划；不能只在await之前读一次remaining。
- 只有实际选中并成功交付的内容记为delivered，被预算淘汰的条目不记为已发送。
- 保留“芯片优先，召回使用剩余额度”，没有新的单独300池。

### 澄清compaction边界

本轮明确采用严格的**同一用户轮累计300**：预算身份是workspace+session+稳定用户事件；compaction generation用于去重/在途操作失效，不给同一用户事件凭空重置spent。

同轮compaction后需要重建时，只使用该轮剩余预算；不足则在UI说明待下一用户轮。开场地图400是独立的一次性预算，不能每次压缩又免费追加400。若要采用“每个压缩窗口重新计费”的其它产品语义，必须作为明确的契约变更回交，不可继续宣传“同一用户轮累计300”。这条澄清优先于旧计划中容易产生歧义的“压缩后清账本”。

### 稳定轮标识

优先使用宿主message id或用户事件seq；从session/event记录规范身份，并在pre-step中复用。内容相同的两条不同消息是两轮；消息对象重新构造仍应认出同一轮。只靠WeakMap对象身份不能证明宿主兼容。

没有可验证的稳定标识时，必须给出可观测的保守降级，不能按文本、时间、pre-step次数或新的对象实例反复发放额度。通过真实宿主的多工具步骤验证，而不只重复传同一个mock对象。

### 验收

- 审查的三条长pins fixture：首步217，剩余83；后续不再投递装不下的另外两条，累计保持217，绝不出现651。
- pins+recall两个消息块的包装计入；零预算、双commit、rollback、并发reservation、旧generation均有断言。
- 同文本不同事件可开启新轮；同事件克隆对象、工具循环不重置预算。
- 同轮compaction不突破300；新用户轮可正常重新分配。
- 通过实际 `agent/pre-step` 钩子收集发送文本并计算累计值，不用UI上的planTokens代替。

## 5. R3 身份明确、全图验证、原子导入

涉及：`lib/store.js`、`lib/sidecar.js`、`lib/revision-graph.js`、`lib/revisions.js`、`lib/server.js`。建议新增共用 `import-plan.js`，JSON与JSONL只负责解析和各自的合并/同步语义。

### URI规则

- 有稳定URI：仅与相同URI匹配；URI不在库中则计划新建，不走文本模糊合并。
- 不同URI的版本节点，即使名称相同、正文完全相同或相互包含，也必须保留独立身份。
- 缺URI的旧v1数据：普通独立事实可保留现有兼容回退；参与版本关系的节点必须建立明确的一对一身份。无法消歧就报冲突，不猜测合并。
- 同一导入内重复URI、重复导出id、映射冲突必须写入前发现。

### 先计划再落盘

1. 解析并验证格式、字段、卫生与版本。
2. 在统一的workspace写入临界区中，为所有输入节点建立计划映射；这一步不调用insertNode/mergeInto等会persist的函数。
3. 基于映射，计算导入完成后的完整图：已有关系、新关系、该同步模式要求的普通边删除/归档都在其中。
4. 验证这一张最终图的自环、循环、线性链、节点类型、端点状态、32跳及历史正文保护。不能只验证原始导出id图，也不能只验证新增边。
5. 一次提交所有事实操作：新节点、payload更新、普通边、supersedes边以及该同步应做的归档/删除。JSON合并导入与JSONL全量同步的既有语义分别保留，不能混为一种。
6. 事实提交成功后，再维护独立文本索引和JSONL写出；错误按所处阶段报告。

### 对insertWithId方案的决定

**有条件接受“安全预分配id + insertWithId/upsertEdge同一原生事务”**，这是优先方案。TriviumDB 0.8.11的TransactionOperation确实支持这两个操作，但类型声明并不证明任意id分配方式都安全。

实现者必须先在独立库验证：

- id满足内核范围与JS安全整数约束，不碰撞现有节点、同批计划或其它写入口；不能分散在多个循环里临时猜next id。
- 分配、图校验和提交共享一个串行边界；普通写入、抽取、sidecar应用不会插队破坏计划。
- 事务内后续边能引用同事务insertWithId创建的节点。
- 事务失败时节点、URI、payload、向量与边在逻辑上均未改变；重开后也一致。
- 事务成功后再调用普通db.insert，不会覆盖刚导入的节点；重开后连续分配仍正确。
- 高id/已有删除空洞不会引发不可接受的分配行为。不得假定有未公开的nextId或临时id API。

若无法证明以上条件，提交替代方案供审查；不能退回“先写事实、再写边、失败算部分成功”。临时阻止有风险的导入也必须在首次写入前完成。`reserveNodes()`只是容量预留，不是id预留。

### 错误与衍生数据

- 预检冲突：结构化失败，数据库逻辑内容保持原样；常规冲突409，输入格式错误400。
- 原生事实事务失败：返回 `ok:false` 与明确故障，禁止 `ok:true + revisionConflicts`。
- 事实已提交、文本索引/JSONL维护失败：明确“事实已提交，衍生数据待恢复”，不能声称全部回滚。可重试、可观察，重新打开能恢复，不重复应用事实。
- 失败导入不能更新sidecar“已同步hash”，也不能自动覆盖用户尚未成功应用的输入文件。
- 保留模型工具禁止直接写supersedes的限制；导入路径也不能绕过人工历史保护。

### 验收

- 两个URI不同、正文包含/完全相同：导入后仍是两个节点，只有合法新→旧边。
- 导入本身无环、与现库拼接成环：写入前整体拒绝；一对多/多对一身份冲突同样拒绝。
- 注入事务失败后，对比完整逻辑快照并重开校验，不能只检查“没有半条supersedes边”。
- 同一文件重复导入幂等，已有无关节点/边不被误删；JSON与JSONL分别测试。
- 结构校验不是删除真实已归档历史关系：区分“禁止新建带归档端点的替代操作”与“忠实恢复合法历史状态”，避免备份无法往返。

## 6. R4 同轮更正与已发布数据的检查

### 接通生产更正

更新、归档、替代、撤销及成功导入后，把相关状态变化通知曾在当前workspace/session投递该事实的账本。期限自然到期没有写事件，因此pre-step也要比较已投递状态。

指纹包含实际模型可见的事实与状态，不仅是id+l0；来源备注变化等未改变注入内容的编辑，不应导致重复注入。

更正作为专用短消息处理，不能套用“归档/过期的召回候选一律丢弃”后把更正自己丢掉。更正不重发旧全文，与pins/recall共用该用户轮累计300；不足时留到下一轮并显示待生效。成功投递才消费correction，失败保留，重复事件合并，不能每轮无限重复同一条通知。

### 0.5.0数据检查

提供针对版本关系的只读检查函数/维护脚本，检查自环、循环、分叉、缺失端点、重复URI及不可解析的当前版本。用临时库验证只读行为；不得用会创建工作区或自动写索引的openWorkspaceDb冒充只读检查。

诊断只报告问题，不自动删边、不自动拆节点。已经被错误合并覆盖的历史正文可能无法从当前库恢复，不能根据推测重新生成。恢复应使用升级前文件组或原始导出，先预览、另行明确执行。

不把这项收尾扩展成新的图谱工作台或自动修复产品。
