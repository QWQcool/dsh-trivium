## 1. 指标分层与测量层级

每条指标都要写清"测的是哪一层"，混层即作废。本批新增一条分层，因为 B 批实测暴露了它：

- **固定税**：四个工具的 schema 常驻（基线 529 `estimateTokens`）+ 插件常驻提示段。**每轮都在，与召回策略无关。**
- **可变注入**：短地图（≤400，每会话一次）、芯片/更正/召回（共用每轮 300）。

不分这两层，"净节省"会被常驻税淹没：goodmemory 的 0.1.x 首发**不注册任何模型工具**，固定税为 0，而我们是 529 —— 这是结构性差异，必须单独列，不能记成"注入更省"。

| 层 | 指标 | 数据来源 | 测量方式 |
|---|---|---|---|
| 检索层 | Recall@1/@5/@8、误召回、空结果正确率 | 固定查询集 + 金标 URI | 离线，零模型调用 |
| 注入层 | 每轮注入 token（固定税/可变注入分开）、有害注入率、过时事实率、**跨工作区泄漏（硬门槛 = 0）**、同轮预算是否越界 | 插件账本 + 宿主 `usage` | 离线 + 宿主事件旁路 |
| 负载层 | 导入、重开（冷启动）、检索 p50/p95、RSS、`.tdb` 体积 | `scripts/bench-scale.mjs` | 离线，零模型调用 |
| 体验层 | 总量/每题 token、答对所需轮次、p50/p95 端到端延迟 | 宿主 `usage` 真值 + 人工判分 | **需真实模型**，受 §0 预算约束 |

端到端 token 的计费值**只认宿主 `usage`**：`dsh-session` 的 `assistant/message` 事件携带 `TokenUsage`，字段 `inputTokens / cacheReadTokens / cacheWriteTokens / outputTokens` 是**互斥拆分**（缓存命中单独可得）。插件自己的 `estimateTokens` 只用于解释预算，**不当计费值**。

⚠️ 插件侧当前读不到 `usage`（`lib/` 全目录 grep `usage|prompt_tokens` 零命中）。C3 需要一个**只读观测器**：测试 profile 内的旁路插件订阅 `session/event` 落 JSONL。它不进生产路径、不改预算、不随包发布。且 usage 是 per **step**，一轮多次工具调用必须按 turn 求和。

## 4. 数据协议（C1 的硬产物）

1. **正文键是 `payload.text`**，不是 `body`。`ctx_remember` 写 `args.text`，`indexTextFor` 只读 `text`。用错键会造出一个"全零命中"的假缺陷 —— 本轮已踩两次。
2. 名称里的主题这类派生字段，生成与查询必须共用同一函数，否则会自造"召回失败"。
3. 事实集用合成数据，字段与生产写入路径同构；每条事实带 `uri`（判分锚点）。
4. 查询集固定 16 正例（URI / 全文独有片段 / 唯一别名 / 精确名称）+ 3 负例（必须零命中）。
5. 种子固定并写进制品；同一 (tier, seed) 必须生成同一份图。
6. 训练/调参集与验证集分开；场景名、答案、文件名不得暗示答案。

三条已确认事实：

1. **质量没坏，性能崩了。** 正例 15–16/16、负例全对；三档一致。这是纯负载问题。
2. **根因是 O(n) 全扫**：`keywordFallback`（`lib/store.js:1749`）对 `db.allNodeIds()` 逐节点 `db.get()` + 每 term 一条正则。缩放约 n^1.75。
3. **重开成本不成比例**：`openWorkspaceDb` 的 `rebuildTextIndex` 每次打开全量重建 → 50k 下每次重启付 2.3 分钟。

### 7.1 缺陷候选：精确名称命中不保底，召回对图形态敏感

7 次运行中 4 次复现，**失败查询始终是同一条**：`revision note 2`（节点 2 的**精确名称**），被 `revision note 26` / `revision note 2330` 挤出 top-8。

关键证据（本轮新增，且修正了上一版的机制推断）：

- 同一档位内三次重复的**节点 payload 完全相同**（`rand()` 只用于生成边），只有边的形态不同；
- 10k 档：rep0（seed …028）失败、rep1/rep2（…029/…030）通过；
- 因此**不是"同分候选按存储顺序随机"那么简单**：同样的文本、同样的候选集，换掉业务边就会被挤出 top-8。

修正后的判断：

- 已证实：`primaryScore` 给精确名称 4 分（最高档），但结果仍可被 `revision note 26`（3 分）压过 → 说明最终排序不是按 `primaryScore` 单一决定，**图扩散/boost 会改写它**（`scanBusinessNeighbors` + `rankBoost`）。
- 仍未证实：`keywordFallback` 的 64 上限是否也参与（同分候选在 1k 档 111 个、50k 档约 11 万个，理论上会截断）。上一版把它写成主因，属于**过度归因**，已降级为待插桩项。
- 影响不变且更硬：**同一库内容、同一查询，只改边就能改变召回结果**，Recall@k 因此不可重复。D 批若在此时调阈值，调的是对图形态的响应而不是召回质量。

C2 剩余：插桩确认 64 上限的实际作用 + 定位 boost 改写排序的具体位置。

#### 7.1.1 C2c 结论（2026-10-29，用 `searchNodes` 自带 `onStage` 观察，未改源码）

同一份 1k 图、同一查询 `revision note 2`，两个只差边形态的种子：

| 阶段 | seed …028（失败） | seed …029（通过） |
|---|---|---|
| native-hybrid | 含 id3（第 1 个） | 含 id3（第 1 个） |
| keyword-fallback | 含 id3（第 1 个） | 含 id3（第 1 个） |
| entity-anchor | `[3]` | `[3]` |
| business-expand | 157 个邻居 | 154 个邻居 |
| **最终 top8** | `[27,203,219,227,235,243,251,259]`，**目标被丢弃** | `[3,27,203,…]`，**目标排第一（score 4）** |

节点 payload、id、`status: active`、`type: entity` 两例完全一致。

**已否证**：不是"64 个候选截断把目标挡在外面"——三个候选阶段都包含目标。
**新的准确表述**：目标以 `primaryScore` = 4 进入候选后，在**候选之后的展开/排序阶段被整条丢弃**（不是排到第 9 位），且是否发生由边形态决定。`business-expand` 是目前唯一在候选后引入大量节点的环节。

下一步（C2c-2）：在排序段加临时插桩定位具体行，跑完即 revert。**在此之前不写"根因已定位"**。

**C2c-2 已做的否证（2026-10-29，仍未定位到行）**

| 假设 | 实验 | 结果 |
|---|---|---|
| 64 候选截断 | `onStage` 观察三阶段 | **否证**：native-hybrid / keyword-fallback / entity-anchor 都含目标 |
| `rankBoost`（图连通性加 4 分）压过相关性 4 分 | A/B：只给目标加一条 `about` 边，其余不变 | **否证**：加边后目标仍在 top-8 之外，`rank = -1` |
| 分数被邻居覆盖 | 读 `business-expand` 后逻辑 | 邻居记 `score: 1`，不可能压过 4 分 |

现状：`keywordFallback` 已经把目标 id 报给 `consider()`，但目标最终不在 `out` 里。损失点在 **候选报告 → `primary` 之间**，也就是 `consider()` / `hitRecord()` 内部（`hitRecord` 有 archived / workspace / episode / `payloadLooksDirty` 四条 null 出口）。下一步必须临时插桩 `consider()`，逐条打印目标 id 的 `hitRecord` 返回与 `score`。**这是目前唯一能收敛的做法，不再靠推断。**

**C2c-3 根因已定位（2026-10-29，临时插桩 `consider()` 后已 revert，`git diff` 干净、`smoke-p0` 通过）**

插桩输出（失败种子）：`consider 3 rec= ok native= 2.36 → gate lexical= 4 termsHit= true → score 3 4`，目标以 4 分进入 `primary`，但最终结果里没有它。所以损失在 **`primary` 之后**，只剩一步：最终排序。

`lib/store.js:1498` 的排序比较器：

```js
.sort((a, b) => {
  const rb = rankBoost(db, b, text, at) - rankBoost(db, a, text, at);  // ← 第一键：图连通性
  if (rb) return rb;
  const score = (b.score || 0) - (a.score || 0);                        // ← 第二键：相关性
  ...
})
```

而 `rankBoost`（`lib/store.js:1561`）的第一条就是 `if (hasBusinessEdge(db, hit)) n += 4;`。

**完整因果链**：

1. fixture 里 `if (i > 3)` 才加业务边，所以最早两个节点**没有任何业务边**（出向、入向都没有）；
2. 这类孤立节点 `rankBoost = 0`，而所有 20+ / 200+ 号节点都有 `about` 边 → `rankBoost = 4`；
3. 排序第一键把 8 个"弱相关但有边"的节点排在"精确命中但没边"的节点之前；
4. `slice(0, topK)` 把目标切掉，**它连出现在结果里都做不到**。
5. 种子差异也解释了：只有在 `i=5` 时 `rand() < 0.2` 才会生成 `{from:5, to:2, label:"decided"}`，给目标一条**入向**业务边 → `rankBoost` 变 4 → 与其他人打平 → 相关性 4 分胜出，于是排第一。这就是"换个种子就正常"的全部原因。

**这条为什么严重**：

- 不是"排得靠后"，是**整条消失**；`ctx_find` 的 `topK` 默认 8。
- 受打击的恰恰是**刚记住、还没连上新事实**的节点——而"刚记住的东西能不能被找到"是记忆插件的第一性要求。
- 也叫"孤立事实被结构性歧视"：图越稠密，孤立节点越容易被埋。库越大越严重（50k 档正例 15/16 的缺口大概率同因）。
- 我之前两次归因（64 截断、图扩散加分）都是错的，A/B 里我给"节点 3"加边的实验也无效——因为 import 的 `from/to` 用的是**旧 id**，`{from:3}` 指的是 `bench://scale/3` 而不是库里的 id 3。**fixture 的 id 映射又一次误导了结论。**

**D 批候选（本批不改）**：排序第一键不能是图连通性。合理顺序应是"相关性优先、连通性做 tiebreak 或小幅加成"，或至少给精确名称命中一个**保底名额**。具体改法、阈值与回归门槛留到 D，先由 C 记录为"已定位、未修复"。

### 7.3 抽取成本基线（C2d，零模型调用，`scripts/bench-extract.mjs`）

**A 段是实测**：真实 `distill()` + 桩 `llmCall`，抓提示词后用 `estimateTokens` 计数（不是供应商计费值）。

| 累积消息数 | 单次提示词 token |
|---|---|
| 6 | 见脚本输出 `promptSamples[0]` |
| 20 | 1,392 |
| 40 | **2,175** |

提示词随累积轮数增长——这意味着"攒批"会提高单次成本但降低次数，净效应必须算总账。

**B 段是离散事件模拟，不是实测**（真实计时器是 `setTimeout(12000)`，等 40 条消息要等几十分钟）。时间轴：40 条用户消息成簇发送，簇内间隔 20–40 s，簇间 4–10 min。

| 策略 | 触发/天 | 提示词 token/天 | 总 token/天 | 相对现状 |
|---|---|---|---|---|
| **P1 现状：静默 12 s** | **40** | 87,000 | **95,000** | — |
| P1 + 5 min 冷却 | 14 | 30,450 | 33,250 | −65% |
| P2：静默 60 s | 13 | 28,275 | 30,875 | −68% |
| P2 + 累积 6 条 + 冷却 | 13 | 28,275 | 30,875 | −68% |

对照：注入侧按 B5 真机实测 149/300 估算 token × 20 轮 ≈ **6,000 token/天**。

**结论（量级，非最终）**：抽取约为注入的 **16 倍**，是当前默认配置下的主成本；把触发窗口从 12 s 改到 60 s（或加 5 min 冷却）可砍掉约 2/3。

**模拟的已知偏差**：脚本只在用户消息上累加 `pendingMessages`，而助手回复同样会置 `dirty`，所以真实触发次数可能接近 **2×**（约 80 次/天）。这使上表的绝对数字偏保守，但**相对降幅不受影响**。

**为什么现在不改**：这是默认行为变更（属 D 批范畴）。C 先把"改前"数字固定下来，D 再改并复测同一脚本，才能给出可信降幅。改法建议（双阈值取或 + 冷却 + hash 带规则版本号 + `session/disposed` flush）见会话记录与 §8 风险表。

### 7.3.1 抽取降本已实施（2026-10-29，用户授权，独立于 C 的测量范围）

**改了什么**（`lib/index.js`）：

| 项 | 旧 | 新 |
|---|---|---|
| 静默窗口 | `setTimeout(..., 12000)` 写死在 `turn/end` 里 | `scheduleExtract()`：`EXTRACT_IDLE_MS = 60_000` |
| 批量触发 | 无 | `EXTRACT_BATCH_TURNS = 12`（约 6 轮）条 turns 立即抽，不再等静默 |
| 冷却 | 无 | `EXTRACT_COOLDOWN_MS = 5 * 60_000`；冷却期内不清空 buf，内容留到下一个窗口 |
| 重复抽取 | 无保护 | `turnsHash()`（FNV-1a over role:text）判同一批内容不重复调模型 |

**预期效果**（按 §7.3 模拟）：触发次数 40 → 13 次/天，token 95,000 → 30,875（−68%）。

**回归**：新增 `scripts/smoke-p27.mjs`，替换全局 `setTimeout` 抓"排了多久/有没有排"，不真等 60 s：
1. 10 条 turns 后 `turn/end` → 排一个 60,000 ms 定时器；
2. 12 条 turns → **不排**定时器（直接 batch 抽）；
3. 抽完立即再攒 → 冷却生效，改为重新排定时器。
`node scripts/run-all.mjs` → **28/28**。

**实施中发现的一个真实故障模式**：`scheduleExtract` 最初写成模块级函数，直接调 `optionsOf()`——而 `optionsOf` 是 `apply()` 内部的闭包（`lib/index.js:543`）。调用时抛 `ReferenceError`，被 `session/event` 外层的 try/catch 吞掉，表现为"定时器根本不排"，而 p27 的断言恰好把它抓了出来。**这正是 0.5.0 那个 `remainingOf is not defined` 的同类问题**，说明"新函数必须在能拿到闭包的地方定义"这条约束还得继续靠行为断言守住。

**没做的**（明确记录，不算完成）：

- **#1 本地预筛**（本轮没有决策/偏好句就不调模型）：会改变抽取质量，需要单独评测，未实施。
- **`session/disposed` 的 flush 未新增**：核查后发现已有 `savePending` + 下次 `pre-step` 的 `pending-replay` 兜底，**我此前说"必须加 flush"是错的**，不需要重复实现。

### 7.3.2 去重回归（`scripts/smoke-p28.mjs`，2026-10-29）

p27 只测了"什么时候排定时器"，`turnsHash` 的跳过路径没有证据。p28 补上：

| phase | 输入 | 期望 | 实测 |
|---|---|---|---|
| 1 | 12 条 turns + `turn/end` | 调模型 1 次，失败后落盘 pending | 1 次 |
| 2 | 时钟前进 10 min，推入**完全相同**的 12 条 | 仍 1 次（去重跳过） | 1 次，`same: true` |
| 3 | 最后一条改一个字 | 变 2 次 | 2 次，`same: false` |

判据用**模型调用次数**（llm 桩一调就抛，因此必然走 `llmFailed → savePending`），不依赖文件时间戳。`run-all` → **29/29**。

**写这个回归时踩的两个坑，都记下来**：

1. **`settle()` 用固定 sleep 150 ms 不够**：`runExtract` 要先 `openWorkspaceDb`（含文本索引重建），超过 150 ms，于是 phase 2 推入时缓冲区还没清空 → 24 条 turns → 哈希不同 → 误判"去重失效"。改成**轮询等 pending 落盘 + 再等 400 ms**。
2. 插桩 `lib/index.js` 时我先用脚本做字符串替换，替换其实没命中（`grep -c P28_DEBUG` 为 0），却因为打印了"instrumented"而以为生效，白跑一轮。**"脚本声称成功"不等于"改动落地"，必须 grep 验证。**

结论：抽取降本的 2 项（触发策略 + 去重）现在都有行为回归；#1 预筛仍未做。

### 7.4 注入层与正确性硬门槛（C2a，`scripts/bench-injection.mjs`）

走真实插件路径：`registerTools()` 拿四工具、`plugin.apply()` 拿宿主钩子、真实 `agent/pre-step`。合成库 + 临时 `DSH_TRIVIUM_SETTINGS`，零模型调用。

| 门槛 | 实测 | 阈值 | 结果 |
|---|---|---|---|
| G1 跨工作区泄漏 | **0**（6 条查询 × `ctx_find` 与 `pre-step` 两条路径 = 12 次机会） | = 0 | ✅ |
| G2 同轮注入预算 | **76 token 累计**（第 1 步 76，第 2–4 步 0） | ≤ 300 | ✅ |
| G3 过时事实 | 标 `stale` ✅；`include_stale: false` 时返回 `No memory hits.` ✅ | 两者都要 | ✅ |

**G2 的第一次测法是错的，记录在此**：最初每次 `preStep` 都新建一条用户消息，于是每一步都被判成新的一轮，测得"每步 76、从不累计"，看起来永远合格。真实语义是 `turnKeyOf()` 用**宿主 id 或消息对象身份**判轮（工具循环里宿主复用同一条用户消息对象）。改成复用同一个 `msg` 对象后才是有效测量：第 1 步 76，后续步骤 0（同轮不重复投递），累计 76。

结论：三条硬门槛在当前默认配置下通过。G1 的样本量偏小（12 次机会），C3 的真实会话回归里要扩到更多查询。

**两条测法被我自己推翻，记录在此**：

1. 最初把"34 跳超长链"当预期失败，实际是**我的 fixture 让同名节点被 `mergeInto` 合并**，链根本没建起来。改名后才发现真机制是**写入侧就拒绝第 33 跳**——`currentHeadOf` 的 `too-long` 分支在正常路径下永远走不到。
2. 随后想用 `ensureLink` 绕过 API 造环，结果 `ensureLink` 本身就拒绝 `supersedes` 标签（`revisions.js` 的 `refuseModelRevisionLabel`）。所以"损坏链被投影为正常事实"这个失败模式**无法用公开 API 构造**，只能靠直接改 `.tdb` 文件或引擎级注入——超出本批范围。

结论：G4 在可构造的范围内全部通过；`resolver` 返回 null 的两条分支（`cycle` / `too-long`）代码存在但**没有可构造的输入**，因此只能记为"未覆盖"，不能记为"已验证"。








## 8. 风险与停止条件

| 风险 | 影响 | 处置 |
|---|---|---|
| goodmemory pin DSH `0.1.0-rc.8`，本机宿主是 `0.2.1-rc.4` | 可能装不上或激活即失败 → C4 主臂没了 | C4 第一步先验装载；失败则如实记为"未覆盖"，不换别的插件充数 |

| billion-context 是代理，要改 baseURL | 会改变宿主链路，污染其它实验 | 独立 profile + 独立 `DSH_HOME`，跑完即拆；不与 C3 共用 |
| 15 元预算被前几轮吃光 | C3 覆盖不足 | 先 10 场景 pilot 估算单场景成本，再决定 30 场景是否可行 |
| 50k 档 18 分钟导入 | 单轮 25 分钟、3 重复 75 分钟 | 只跑 1 重复，其余重复在 1k/10k 档做；在报告里注明 |

停止并回交的条件：预算超限；对手插件在本机装不上且无等价替代；出现需要改默认行为/加工具/加服务才能继续的诉求；C2 结论不足以支撑 D 的候选方案。
