## 1. 硬筛条件

与 D 批要回答的问题（"值不值得改召回策略"）直接相关，因此只有同时满足以下四条才进对比池：

1. **同宿主**：能装进 `@deepseek-ai/dsh` 0.2.1-rc.x，走同一个 `agent/pre-step` 语义。跨宿主的对比直接失去可比性。
2. **无强制外部服务**：不需要另起常驻服务、容器或云凭据。否则延迟与失败模式混进结果（OpenViking 就栽在这里）。
3. **预算可调/可读**：能读到或改到它的注入 token 预算，否则无法构造"等预算臂"。
4. **Windows 可跑**：本机是 Windows；异构运行时（Python 服务、Bun 缺失）先算作未覆盖。

复核补充：goodmemory的managed bridge仍是本地子进程/HTTP服务，并非与我方同样的纯进程内实现。“无强制外部服务”筛选与该候选的含义须在C4开工前明确，不能用managed一词抹掉运维和延迟差异。本轮没有启动它，也没有改变我方服务架构。

## 3. 三条已经影响设计的事实

### 3.1 默认预算差 4.7 倍，"默认安装横跑"一定不公平

| 对手 | 每轮注入预算 | 相对我们（300） |
|---|---|---|
| goodmemory | 256 | 0.85× |
| dsh-memory | 800（检索块）+ 600（常驻块）= **1400** | **4.7×** |

所以 C4 必须有三档预算臂，而不是"各用各的默认"：

| 臂 | 注入上限 | 目的 |
|---|---|---|
| 等默认 | 各自默认 | 回答"照原样装，用户实际会看到什么" |
| 等预算 300 | 全部压到 300 | 仅控制注入预算这一变量；还需固定语料、抽取、provider、提示和判据，不能单独归因召回算法 |
| 对齐对手 | 我们抬到 800/1400 | 回答"如果我们放预算，能不能追上/超过"（只测不默认开） |

### 3.2 工具常驻税差 0 / 27 / 10 / 4

goodmemory 0 个模型工具、dsh-memory 27 个、mneme 10 个、我们 4 个（529 估算 token）。
工具 schema 是**每轮常驻**的固定成本，必须和"可变注入"分开报。否则"它注入 800 token、我们 300"这种数字会得出完全相反的结论。

### 3.3 dsh-memory 的增量索引正是我们 50k 问题的反例

它 v0.9.8 起明确"启动/巡检不再全量重建派生数据，O(新增+尾部) 而非 O(全量)"；而我们的 `openWorkspaceDb` 每次 `rebuildTextIndex()` 全量 → 50k 档重开 2.27 分钟。

这条让 C4 从"谁更强"变成"一个已被别人解决的问题我们为什么还在付"——比任何排名都值得写进报告，也直接喂给 D 的候选。

## 4. 取舍：最多三臂，理由是可归因性不是热情

每多一个臂，成本不是"再跑一次"：

```
装载验证（可能装不上） → 等预算配置 → 场景跑 → 人工判分 → 差异归因
```

按 §0 的 15 元/次预算与 10 场景 pilot 估算，**臂数超过 3 时，每个臂的样本量会小到无法区分噪声**。因此：

| 优先级 | 臂 | 不可替代的信息 |
|---|---|---|
| P0 | 我们自己四臂（无记忆 / 仅地图 / 当前默认 / autoRecall） | 基线噪声 + 我们内部哪个通道有用 |
| P1 | **dsh-goodmemory** | 同宿主同语义下"自动写回 + 自动召回"的对照；固定税为 0 的极端 |
| P2 | **dsh-memory（34262315716）** | 1400 预算 + 三路 RRF + 增量索引；回答"向量与更大预算值不值" |
| P3（有余量才做） | dsh-mneme | 唯一能测后台整理（autoDream 默认开）的 token 成本 |

billion-context 不进主表：它回答的是"要不要记忆"而不是"哪个记忆更好"，放在报告的"替代方案"一节。

## 6. 抽取/写入成本对比（2026-10-29 补，回答"我们抽取是不是最贵"）

注入预算只是成本的一部分。各家**默认是否频繁调用模型**差异更大：

| 项目 | 默认抽取方式 | 默认是否为此调用模型 | 依据 |
|---|---|---|---|
| **dsh-trivium** | 本地规则候选 + 可用时的宿主模型蒸馏 | 抽取默认开；8ef31f8后为60s静默/12条批量/5min冷却，不再是12s。此表不能据此推导真实每天账单 | 当前源码，抽取成本模拟见C计划 |
| dsh-memory | `features.autoWrite: true` + `valueGate` + `dedupMerge` 的**规则/启发式写入**；`refiner.enabled: false` | **否**（refiner 是可选增强，不是默认路径） | 一手 README 配置默认值 |
| dsh-fish-memory | "提炼"与"扩词"两步调模型 | **点了才调** | 一手 README："不点它们就不会调用" |
| dsh-mneme | `autoDream` 去重/合并/修正 | **是**（`autoDream: true` 是默认） | 一手 config 默认值 |
| dsh-goodmemory | 写回用户全文 + 最终助手文本，交给 GoodMemory 自带提取策略 | 取决于 GoodMemory（其 receipt 有 `extraction strategy` 字段，说明策略可变） | 一手 README |

不能据此断言“我方关掉模型就没有类型化节点”：`distill()`始终先生成规则候选，没有llmCall时也可写类型化事实；而`extractEnabled:false`会暂停整个自动抽取，显式工具仍可写。模型增强、规则抽取、整个抽取开关是不同层级；默认成本必须测量，不能从README架构话术推导。

**关于"本地预筛"是否等于"扩词库"**：不是同一层。预筛是 `gate`（这一轮要不要调模型），分词/词表是 `match`（能不能搜到）。预筛**可以**借词表实现（决定/改成/以后/别再/约定/偏好…），但扩词表只能减少**误调**，不能消除**漏抽**——口语表达无边界，规则二分类必有 false negative。因此预筛必须默认偏保守（宁可多抽），并用 C 的数据校准，不能当成免费的午餐。

**待测**：抽取与注入的成本占比（C3 必测项）。在拿到宿主 `usage` 之前，任何"注入是主成本"或"抽取是主成本"的判断都只是算术假设，不是结论。

## 7. 不做的声明

- 不做"安装即跑"的默认横跑排名（见 3.1）。
- 不把合成场景的胜负写成"真实使用质量"。
- 不用我方插件自报的 `estimateTokens` 当计费值；计费只认宿主 `usage`。
- 不在对手插件的历史 benchmark 数字上做二次宣传；它的数字只用于设计实验，不作结论。
