## 2. 四次失败逐个看

### 2.1 CORRECTION r4 / r5：答成 “A”（真问题）

两次的库里**同时存在**旧约束与新决定，且是**两个独立节点**，不是 supersede 链：

```text
方案 A
先别动旧方案 A，我们还在评估。
不再使用旧方案 A，改用方案 B。
```

抽取把“先别动 A”和“改用 B”分别写成了 decision，没有把后者标成前者的后继。于是短地图里两条并列，模型这次选了 A。**这不是抽取漏，是“哪个是当前版本”没有被建模。**

### 2.2 NEGATION r5：回答为空（未定位）

库里有正确事实（“一律不得自动执行，必须先经用户人工确认”），但提问轮 `final` 是空字符串。当前证据不足以判断是模型空回、还是那一轮提前结束；需要在该轮抓 `stop_reason` 与 turn/end reason。

### 2.3 REFERENCE r2：自相矛盾（判负，但记忆其实生效了）

```text
"没有记录生产端口，无法给出数字；记忆里只有预发布环境的 9443。"
```

判分按“出现否定词就判负”的规则给了 FAIL；它其实读到了 9443。**这条更该记成“回答组织能力问题”，不是记忆失败**。判分口径要单独修，不能靠一条正则同时抓“没有记录”和“我记不清”。

### 2.4 顺带发现的幻觉

CORRECTION r4 的落库文本里出现：

```text
On 2026-04-06 (per conversation context), user corrected: no longer use old Plan A, switch to Plan B.
```

实际对话日期是 2026-10-30。抽取 prompt 明确要求“把日期留在事实文本里”，模型却**编了一个日期**。这条会被后续当成真实时间线使用，属于要单独治的缺陷（当前无日期校验）。

另外：中文输入常被抽成英文（`Do not auto-publish; publishing requires explicit manual user confirmation.`）。这本身不算错，但**判分必须按语义**——A-5 的否定场景就是因为一开始只认中文“确认”，把 5/5 误判成 0/5。

## 3. A-5b：真实压缩尝试（放弃，但拿到了证据）

做法：用代理给**第一个带工具的 agent 请求**注入一次 `context_length_exceeded`，让宿主走它自己的“总结 → 重试”路径，然后在新会话问同一个事实。

发生的事：

```text
#1 status=400 injected=context_length_exceeded  bytes=83678  tools=29
#2 status=200                                   bytes=50695  tools=0    ← 总结调用
#3 status=200                                   bytes=81336  tools=29   ← 重试成功
...
#43 （仍在继续）                                 bytes=273725 tools=29
```

压缩链路本身是通的（400 → 总结 → 重试）。但之后那一轮进入了**长工具循环**：43 个请求还没结束，请求体从 84KB 涨到 **273KB**（工具结果不断累积）。我在命令超时后终止了这次运行，所以**压缩后的召回结论没有拿到**。

已花费 ¥0.079235，证据：[compact-attempt-requests.json](evidence-r3/a5/compact-attempt-requests.json)。

下一轮重跑前必须先加两道闸：**每轮超时**、**单轮请求数上限**（例如 12 个请求或 15 分钟就中止并记录），否则单次实验可能无声地烧掉几块钱。

## 5. 下一步建议（含评测节奏）

1. **先修“取用”，再扩样**：CORRECTION 2/5 的根因是两条决策并列。最小修法是让抽取在写新决策时尝试 `supersede` 旧决策（或至少在短地图里把“更新于/取代”标出来）。这比继续加重复次数更有价值。
2. **日期幻觉**要在写入前校验（例如拒绝晚于当前时间或与消息时间差超过 N 天的日期），或干脆不允许模型在正文里写绝对日期。
3. **判分口径拆开**：`没有记录` 与 `我记不清` 分开；REFERENCE r2 那种“先否定后给出正确值”应判“需人工复核”，不要一律判负。
4. **压缩实验**加超时/请求数闸后重跑 3 次，这是唯一还空着的关键格。
5. **评测节奏**：不必每改一行就全量。建议
   - 每次改动：`run-all`（零费用）+ 单场景 1 次冒烟（约 ¥0.01）；
   - 每轮功能收口：A-5 的 25 轮（约 ¥0.3）；
   - 只在**引擎/模型/宿主**变化时重做全量基线。

## 6. 关于 TriviumDB 0.9.0 还没发布

- 本项目 `package.json` 里是**精确版本** `triviumdb: 0.9.0-beta.3`，不是 `^`，所以换机会装到同一版，结果可复现。
- 上游当前：`latest = 0.8.11`（稳定）、`beta = 0.9.0-beta.4`（2026-10-29 发布）。我们比最新 beta 落后一个版本，且 beta 是**每天一发**（beta.1 10-25、beta.2 10-26、beta.3 10-28、beta.4 10-29）。
- 建议：**不要追 beta**。等 0.9.0 稳定后再做一次“兼容性复跑”（1 个场景 × 3 次，约 ¥0.05）确认没有行为漂移即可，不必重做 25 轮。真正需要锁的是：DIM=1536、数据格式、`.tdb` 读写路径——这三样变了才值得重跑全量。
- 风险声明：本基线是 **beta.3 上的行为**，不能直接当成 0.9.0 正式版结论；文档与对外表述都要带这个前提。
