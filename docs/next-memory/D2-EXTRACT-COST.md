# D2 抽取成本专项：检索省下的钱，被写入吃掉多少

日期：2026-10-29。承接 [D1 结果](D1-RESULTS.md)（检索侧 10 轮会话省 0.51× prompt）。
所有价格按 [成本口径](COST-MODEL.md) 的**谷价**。

## 1. 为什么要单独测

D1 的事实是测试直接种进库的，**没有计入写入侧**。而 D1 的净收益 = 检索省下的 − 抽取花掉的，
后者此前只有一个从 C 批推来的粗略数（约 2.4k token/次）。这次用真实提示词与真实模型把它测准。

## 2. 方法

- 用 D1 的同一批 10 轮会话稿（3 个会话，含 3 条约定 + 填充轮），走 `lib/extract.js` 的
  **真实** `buildExtractPrompt()` 与真实 `parseModelJson()` / `filterCandidates()`；
- 三种策略：
  - `perTurn`：每个用户轮一次抽取（15 次调用）；
  - `batch`：整段会话一次抽取（3 次调用）；
  - `rules`：只用规则候选，零模型调用；
- 判"抽取到了没有"：3 条约定里的关键值（如 `DEMO-71`）是否出现在候选里。

18 次真实调用，谷价 **¥0.00795**。

## 3. 结果（每会话平均）

| 策略 | 调用 | prompt token | 谷价费用 | 抽到的事实 |
|---|---:|---:|---:|---:|
| `perTurn`（每轮） | 5.0 | 1038 | ¥0.00179 | **7/9** |
| `batch`（整段一次） | 1.0 | **342** | **¥0.00086** | 6/9 |
| `rules`（规则） | 0 | 0 | ¥0 | **0/9** |

两个事实：

1. **批量抽取把写入侧压到 1/3**（1038 → 342 token，费用 −52%），代价是召回少 1 条（7/9 → 6/9）。
2. **纯规则抽取抽不到这三类事实**（0/9）。它省下的不是成本，是能力。

## 4. 与 D1 对账：净账仍是负的

D1b（10 轮，6 个会话，谷价）：

| 项 | 每会话 |
|---|---:|
| 不压缩无记忆 | ¥0.002712 |
| 压缩 + 我方记忆 | ¥0.002310 |
| **检索侧省下** | **¥0.000402** |
| 减去 `perTurn` 抽取 | −¥0.001790 → **净 −¥0.001388** |
| 减去 `batch` 抽取 | −¥0.000860 → **净 −¥0.000458** |

**结论：10 轮会话、谷价、含抽取，净成本仍是负的。** 检索侧确实少了 49% 的 prompt token，
但**省下的大多落在缓存价上**：`none-full` 的 15660 prompt 里有 5376 是缓存命中（¥0.02/M），
而抽取花的是未命中输入（¥1/M）+ 输出（¥4/M）。**按 token 数看是赚的（省 1268、花 342），按钱看是亏的。**

粗算回本点：检索侧每会话省 ¥0.0004（10 轮），批量抽取要 ¥0.00086 → 需要约 **16–20 轮**才能翻正
（外推，未实测；历史越长省得越快，因为压缩后的历史是线性增长而注入是常数）。

## 5. 可落地的下一步（按性价比）

1. **按内容门控再抽取**：本轮 `perTurn` 对每个用户轮都调了一次（含"继续推进第 N 项"这类填充轮）。
   只对"含决策/约定/偏好"的轮触发，等于把 5 次降到 1–2 次，成本立刻接近 `batch`，而召回不必降到 6/9。
2. **批量窗口**：把同会话的多轮攒到一个窗口（现成的 `batchExtract` 就是这个方向），
   但要用"抽到的事实数"当质量门槛，不能只看便宜。
3. **压输出**：抽取输出是结构化短 JSON，`maxTokens` 400 是保守值；配合上面的门控再压。
4. **换执行侧**：抽取可换本地小模型（成本≈0）或规则+LLM 混合（规则先给候选，LLM 只做确认）。

## 6. 未覆盖

- 只有 3 个会话、1 个模型、1 轮；方差未测。
- 只测"抽到没抽到"，没测抽到的**内容是否正确/去重是否正确**（例如把 3 条约定合并成 1 条也算抽到）。
- 真实 host 的抽取触发路径（turn 结束事件、压缩事件）没有接，本轮直接调提示词；
  因此"每轮一次"是上限估计，实际触发频率取决于 host。
- `batch` 跨会话批处理（把多个会话的轮次放一次调用）未测。
