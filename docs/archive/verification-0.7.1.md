## 截图发现的原生下拉配色问题

用户截图 3 / 7 中，深色宿主内展开原生 select 后，菜单为白底但候选文字不可读；截图 4 可选出 #3，说明不是空候选。修复为所有原生 option 同时指定宿主成对主题变量 `--dsw-alias-label-primary` / `--dsw-alias-bg-base`，以成对系统颜色 `CanvasText` / `Canvas` 回退，覆盖替代选择、类型筛选、合并选择。保留原生 select 的键盘语义，不引入第二套主题或自定义 combobox。代码检查与现有 p18/p24 回归不能替代 Windows 原生弹出菜单的视觉复验。

原始截图包含浏览器其它标签等用户环境信息，仅在本地临时附件中查验，不随公开仓库发布。原始文件名后缀：`bec5fde1`、`1f4660a8`、`3d3b4022`、`d2ea82ad`、`6758374a`、`16c9289e`、`e4d74c2b`。

## 双浏览器截图发现的冲突后旧列表

用户截图 `cf0c3ccb` / `a44ca781` 为 Chrome，`4e743467` 为 Edge（浏览器归属按用户说明）。Edge 将 #2 替代为 #3 后，Chrome 尝试 #4 被 409 拒绝，但关闭弹窗后默认列表仍显示 #2 为当前条目。后台关系没有被覆盖；问题是前端冲突分支未刷新列表。

修复提交 `c16145a`：409、手动刷新状态、成功替代和撤销冲突均同步列表，失效来源/详情/历史缓存并拦截迟到响应；保留编辑草稿与弹窗比较快照，不自动重发 POST。旧按钮被过滤后焦点回到面板标题。若原目标也不再可选，保留禁用的原选择和比较文本，要求重新选有效目标后才能确认。刷新文案不再承诺原操作一定能重试。

同一真实组件回归先复现“没有状态刷新请求”，修复后 p24 12/12；原关系 API 快照保存于 `.tmp/reliability-0.7.1/two-browser-conflict-state.json`，随后只重置合成验收关系供用户复测。配色后的候选包 `5f5b79b957cb9bff4e650568f16ab45bfd648b5d` 也因此失效，不能作为最终发布包。

## 实际 Web 宿主导入故障演练

通过独立只读文件句柄以 `FileShare.None` 锁住合成库 `trivium.jsonl`，没有更改真实用户库或文件权限。向 3097 的 `/api/dsh-trivium/import?cwd=workspace-a` 导入一个固定 URI 的偏好：响应 `ok:true`、新事实存在；旁路定时写出在 rename 阶段得到 `EPERM`，按库 health 为 false。

释放句柄后调用同一宿主的 `/sidecar/generate`，生成成功，health 为 true，导入 URI 在事实库恰好一条并出现在 JSONL 中。故障和恢复输出分别是 `.tmp/release-0.7.1/host-import-fault.json`、`host-import-recovered.json`。这是实际宿主/实际文件锁/实际 HTTP，不是 mock；发起方式是 API，未冒充用户通过 UI 上传。
