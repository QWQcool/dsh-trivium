# 记忆与上下文插件调研：dsh-trivium 的位置和后续路线

检索日期：2026-10-28（Asia/Shanghai）。发布基线：`dsh-trivium@0.7.0`（`4fe638f`），`triviumdb@0.9.0-beta.3`。

**发布基线与本轮工作树要分开。** 0.7.0 已有预算、更正、事务导入与体检机制，但本轮查验仍发现 JSONL 同步、通知时序、版本链边界和前端请求等缺陷；这些机制存在，不代表所有路径正确。未发布的修复、红→绿证据和残留风险见[本轮缺陷审计](bug-audit-2026-10-28.md)。下文讨论产品定位与设计取舍，不把本轮修复追认成 0.7.0 发布时已经通过。

本文是源码和产品设计调研，不是竞品安装验收或横向性能评测。通过 GitHub 连接器读取了 11 个仓库的一手 README，并用检索到的提交重新读取，确认 README blob 与当时默认分支一致；另检查了部分设计文档和代码。文末给出固定提交链接。没有运行这些竞品，也没有采用它们宣传中的性能数字作为本项目结论。

## 1. 结论

适合继续发展的定位是：**DSH 工作区内、默认克制、可追溯且可更正的图记忆**。先把“为什么记、为什么召回、模型收到了哪个版本、出了错怎样恢复”做完整，比继续堆工具、做完整图谱工作台更有价值。

目前最值得借鉴的是：GoodMemory 的写入回执与跨进程验证、Mnemon 的逐轮读写凭据和候选采纳、dsh-auto-memory 将“相关”与“现在需要”分开的评估方法、OpenViking 的宿主兼容流水线、Graphiti 对事实时间与记录时间的区分。借鉴机制不意味着接入其后端或复制其产品体量。

我们有明确的结构优势，但没有已验证的速度、质量或成本优势。单进程、四工具、300 估算 token 的轮预算可以从源码证明；“更快”“更准”“总成本更低”必须在相同数据、模型和硬件上测量。

## 4. 我们的优势区间与不足区间

| 使用场景/维度 | dsh-trivium 当前适配度 | 依据与限制 |
|---|---|---|
| 单用户、单工作区的项目偏好和决策 | 强 | 工作区 `.tdb`、四类业务事实、业务边、显式决策版本链；管理成本和接口面较小 |
| 希望手动控制哪些记忆进入对话 | 强 | 默认关闭自动召回和芯片；人工白名单；pins/更正/recall 共用每轮预算。默认关闭也会让“装完就自动想起”的期待落空，需要解释默认行为 |
| 旧事实已进入上下文，后来被改正 | 有特色，但需完成正确性收尾 | 更正队列按会话和工作区跟踪，设计上送达才消费；有新版本归一、只读体检。本轮发现通知时序缺陷并修复；仍需长期持久化/重启语义与压力验证，不能宣称完整审计系统 |
| 需要说明事实之间为什么有关 | 强于纯条目列表的表达能力 | 业务边及入出边路径可解释；实际回答收益仍未做受控对照实验 |
| 同义改写、跨语言、弱词面重合 | 默认路径偏弱 | embedding 默认关闭，主要依靠词法、别名、实体锚点和图邻居；打开向量也不等于质量已证明 |
| 大量文件、网页、PDF 的资料检索 | 不在当前目标内 | 没有 OpenViking/PowerContext 那类文档摄取与资源管理；不要把一次性 Markdown 导入包装成文档 RAG |
| 多设备、多用户、多进程同时使用 | 偏弱/范围外 | Git 旁路可交换业务事实，但不是完整本机备份或实时协作；同库只有一个读写进程 |
| 历史对话检索与一键回到原始证据 | 偏弱 | 已保存来源/摘录不等于宿主仍可访问该会话；没有可用定位接口时只能明确显示不可用 |
| 运维与分发 | 有利有弊 | 不另起服务；但依赖原生模块与 beta 内核，Node/ABI/宿主 RC 升级仍需验包；所谓“一个文件”应说明实际文件组 |
| 可用性和产品完成度 | 需要补强 | 设置页面可查改，但仅支持 ≥900px；UI 面板、键盘、状态解释和真实桌面验证仍有改进空间。工具少不等于 UI 已简单 |
| 性能、成本、准确率 | 尚不能排名 | 23 组正确性测试不是检索质量或压力基准；300 是自定义 token 估算预算，不是某模型 tokenizer 的精确上限 |

“本地”需要拆开表述：存储在本地，业务检索可无远程 embedding；但 `lib/index.js` 的 `makeLlmCall()` 会通过宿主 `ctx.llm.stream()` 调用当前 provider/model 进行抽取。因此不能无条件声称“抽取全部在本机”或“对话绝不外发”。本地模型还是远程模型由宿主配置决定。该文案问题已交给本轮主审处理。

## 5. 借鉴清单：收益、代价、优先级

| 建议 | 收益 | 引入后的代价/副作用 | 建议范围 |
|---|---|---|---|
| 写入回执：created / merged / rejected / queued，带原因 | 用户能知道“说了记住”到底发生什么；排查漏记 | 需要稳定事件/操作 ID，避免日志暴露正文和密钥；不能把队列接收当成成功落盘 | 高。复用现有 API 与详情区，不新增模型工具 |
| 一轮读写凭据：候选→选中→实际送达→更正 | 把“检索到了”和“模型看到了”区分开 | 历史账本有存储与隐私成本，必须有保留期/上限；用户反馈不等于模型实际使用 | 高。先将现有召回检查做清楚，再讨论落盘 |
| 导入预览与恢复说明 | 提前看见新增/更新/版本冲突及派生文件失败，减少数据焦虑 | 预览到提交间可能发生修改，需快照版本或重新校验；预览不能保证提交必成功 | 高。只读 dry-run，共用真实导入规划器 |
| 检索质量数据集 + 注入必要性评估 | 防止“召回更多”被误当成“更有帮助”；适合克制定位 | 要维护人工标签、训练/验证隔离与反例；不能让阈值在测试集上调优后再自证 | 高。先评估，后更改策略 |
| 宿主兼容矩阵和打包 smoke | 提前发现 RC API/peer/桌面 profile 差异 | CI 时间和平台矩阵增加；npm Web 验证不能冒充 Electron 桌面 UI 验证 | 高。借 OpenViking 的机制，保留明确手工桌面层 |
| 经验候选/冲突候选收件箱 | 自动抽取不立即把模糊结论变成长期事实 | 人工处理成本、候选过期和去重；默认全部审批会损害轻量体验 | 中。只给低置信/冲突项，不给每条事实加流程 |
| 决策时间线和 as-of 历史读取 | 继续发挥图和版本链优势，回答“当时为什么这样定” | 数据格式、UTC/本地时间、溯源不完整与迁移成本；自动时态推断可能再次误写期限 | 中。先可视化已有时间字段；任何新时态字段都显式录入/确认 |
| 检索内部通道可插拔、可解释融合 | 比较词法/别名/图/向量各自贡献，不被某一种模型绑住 | 评分归一复杂、向量成本、缓存失效、重排延迟；增加通道可能增加误召回 | 中。待评估集成立后；默认仍用现有轻路径 |
| 备份/导出完整性清单 | 区分 `.tdb*` 文件组备份、业务 JSONL、Markdown 阅读稿 | 恢复需停止写入和检查版本；应先独立临时库演练，不提供未经验证的一键修复 | 中高。比自动修复损坏链更先做 |
| 独立 Mnemon Provider 或只读 MCP adapter | 把 TriviumDB 图能力提供给现有工作台，少造 UI | 新包/协议/作用域/生命周期维护，双重注入和数据库锁冲突风险 | 后置探索。先只读离线导出或独立库；不是已实现集成 |

暂不建议：默认开启全量 autoRecall、自动删边修链、自动升级技能、五花八门的常驻检索子代理、多 Provider 主框架、文档解析农场、手机全屏工作台、绕过单写者的并发写入。它们会改变产品定位或信任边界，当前收益证据不足。

## 6. 当前设计哪些该保留，哪些应收敛

**继续保留**：进程内内核、工作区隔离、四工具的 `find → read` 分工、显式期限而非从正文猜日期、可验证的预算账本、事务导入的设计目标、URI 身份优先、线性版本链、失败不阻断对话。它们解决的是具体 correctness 问题，不应因为代码较多而误判为冗余；其中 JSONL 的全路径原子性需要本轮修复，不能以原有“事务”命名代替行为验收。

**优先收敛**：

1. 设置页和芯片都能新增/归档/删除，应共享同一操作结果和错误文案；两个入口可以保留，但不应产生两套业务语义。
2. 芯片与会话层的用户目标不同：前者控制下一轮记忆，后者浏览 compaction/fork。会话层继续默认关闭、维护到宿主兼容即可；暂不投入成长为完整画布。是否以后拆成独立插件，需要使用证据。
3. `.tdb`、JSON 图、JSONL、Markdown 各有用途，但必须只给每种数据一个清楚的权威和恢复路径；不要把派生索引、同步文件、完整备份都称为“源”。
4. preview、主动 find、自动 recall 的**当前版本解析和过滤原因**应共用实现；读取预算与用户意图可以不同，不必强行把三者语义统一。
5. UI 的高频操作放在条目列表/详情，低频配置折叠；版本/体检/派生文件错误集中显示在“状态”区域。不要让“检查更新”长期占据工作流首位。

以上是设计判断，不替代本轮代码缺陷报告；其中有些共用实现已经存在，下一步应检查接线和覆盖，而不是为了架构图再重写一遍。

## 7. 修复后的五批计划

版本号是建议边界，不是发布承诺。只做验证/文档不需要发布；正式发布仍由用户明确决定。

| 批次 | 建议版本/规模 | 交付与验收 | 停止条件 |
|---|---|---|---|
| A 可靠性收尾 | `0.7.1` 候选，S–M | 本轮已复现缺陷红→绿；全回归、干净包消费；实际桌面 UI/键盘、两独立浏览器进程冲突、真实宿主导入故障；文档单一入口 | 未修数据损坏风险、同轮预算/版本投影退化，或宿主能力缺失 |
| B 日常操作与回执 | `0.8.0` 候选，M | 统一保存/归档/导入反馈；将召回检查变成每轮投递凭据；导入 dry-run；错误可定位并给出恢复动作；≥900px/键盘/中英验收 | 需要新工具、新默认自动行为或数据格式破坏时先收范围 |
| C 质量和负载基线 | 独立工程批，不必发版，M | 固定合成/授权数据、查询金标、故障案例和 1k/10k/50k 节点档；报告质量、估算 token、p50/p95、RSS、启动/重开/导入耗时 | 数据授权不明确、评测答案泄漏、结果不可复现；不得拿纯合成跑分宣称真实使用效果 |
| D 有证据地改善召回 | `0.9.x` 候选，M | 只选择 C 中最明显的失败类（同义、别名、图扩散或多语）；一次只改一个通道/阈值；报告有益与有害变化；默认 autoRecall 仍关 | 无稳定收益、误召回/跨域泄漏增加、延迟超过预先阈值 |
| E 图特色延伸 | 单独产品讨论/试验，M | 先做决策时间线、来源质量提示、经验的失败→修复路径；按需探索显式 as-of 查询或独立只读 adapter | 自动推断期限、自动裁定矛盾、自动迁移/修链、多进程共享写等改变契约 |

内核稳定版迁移是独立依赖任务：先确认上游正式发布及 API/数据兼容，再从精确 beta pin 切换并重跑回归、打包和真实宿主。不要把它和召回策略、数据格式改动堆在同一批。

## 8. 如何建立可信的质量/性能结论

先测自身的“无记忆 / 当前配置 / 一个候选改动”，再考虑竞品。不同产品的默认捕获、embedding、原文保留和工具预算不同，默认安装横跑不能隔离因果。

- 固定插件/内核/宿主版本、Node、硬件、线程、模型/embedding、数据规模、边数量与缓存协议；分别记冷启动和热查询。
- 分开计：检索 Recall@k / 排名、自动注入精确率/有害注入率、版本过时率、跨工作区泄漏、回答正确率，以及总模型调用/输入输出成本。
- 负例至少包括：提到旧方案但需要当前方案、同名不同工作区、相关但无须注入、用户复述已有事实、显式问历史、过期但主动检索、损坏链、预算不足和模型不调用工具。
- 质量标签由人确认；训练/调参集与最终验证集分开，不能让场景名、答案、数据文件名提示答案。
- 阈值先作为项目要求声明。例如自动注入新增的跨工作区泄漏必须为 0，已知损坏链不能被投影为正常事实；p95/RSS 的具体上限先用测得基线和目标机器确定，不能凭空写成已达标。
- 输出可复现脚本、版本清单、原始 JSON 与失败样本。正确性、离线质量、真机交互、真实模型回答质量分别报告。
