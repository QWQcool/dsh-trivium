## 主要问题（按优先级）

### P1：未发布的门控会把明确事实当成填充句，并成功消费缓冲

位置：`lib/extract.js:216–248,552`，`lib/index.js:233`。

`FILLER_CUES` 只匹配前缀；中文姓名、数字约束、常规中文事实不一定命中线索/专名正则。`shouldExtractBatch` 主要检查用户轮，忽略助手输出里的事实。以下隔离复现全部为 `callCount=0 / applied=[] / gate=filler-only / llmFailed=false`：

- “继续，重试次数改为 5 次。”
- “下一步，项目负责人是张三。”
- “先别管性能，当前生产端口是 9443。”
- 用户“继续。”，助手“采用方案 CedarPlan，发布前需要执行验收。”

由于成功路径会消费该窗口，它们不是延期处理，而是失去模型抽取机会。不能把调用数减少当作无损降本。p36 的正例都是容易识别的线索/英文名，没有覆盖这些反例。

建议：先收窄到整句可确认的致谢/推进表达，检查整个窗口；无法证明无事实时走原有抽取。不要靠增加几条关键词修到只通过本次例子。验收需包含中文姓名、金额/端口/次数、否定/改口、指代、助手与成功工具提供的事实，以及最终持久库和 pending 状态。

### P1：C4/D0 不同臂复用数据库与会话，导致重复种植

位置：`scripts/bench-c4.mjs:213–217,229–232,304–307`。

`armTrivium()` 不接收 arm id，统一传 `trivium-inject` 作为路径，session id 也相同。关闭句柄不会删除数据库。独立复现 S01：第一臂 8 个节点（含工作区），第二臂变为 15 个；新事实 id 从 2–8 变为 9–15。**提交的 D0 账本也记录了这两个臂相同 cwd、不同 id 集合，不只是潜在代码问题。**

同类问题也影响对手：`dsmmemory-800` 与 `dsmmemory-800-min0` 的库路径未含 arm。账本 S01 memories 7→14，S07 12→24。因此“只改 minScore 一个变量”的描述不成立；goodmemory 256/300 也复用库，第二臂已有 duplicate_fact 回执。

建议：所有库路径、会话 id、幂等键、设置/缓存状态都包含 arm/rep/scenario；种植后断言数量、事实集合及规范化 hash，并打乱臂顺序验证顺序无关。修完只重跑受影响的对照，不抹掉旧账本。此问题削弱工具税与对手参数归因；不否定第一臂自身的 S05/S07 直接回归。

### P2：D3 节省计算同时放大旧成本、低估保留请求成本

位置：`scripts/bench-extract-gate.mjs:38–63`。

`summary.perTurn.costOffpeak` 已是三个会话的总额，脚本又乘 `rows.length=3`。随后用所有调用的平均价格估算保留下来的有内容请求，忽略不同输出长度与缓存差异，并把相同均价用于整窗口。

| 量 | 脚本值 | 从已保存账本复核 |
|---|---:|---:|
| 三会话 perTurn 原费用 | ¥0.016107 | **¥0.005369** |
| 保留三个 t0 请求 | ¥0.0010738 | **¥0.002660**（逐请求相加） |
| 整窗口 batch | ¥0.0010738 | **¥0.00258068**（原 D2 实测） |

上述是历史 usage 的计算，不是新门控实测，更不能证明门控不丢事实。`cost-normalize.mjs:44` 还优先遍历 cells，把工具循环的一格算作一次请求：清单实际是 **622 次请求**，汇总“618 次”是格数与请求数混用；这不自动意味着总费用也少算，费用应按 calls 另行对账。

### P2：D1 没有按真实宿主保存注入历史，0.51× 不能当完整会话节省

位置：`scripts/bench-d1.mjs:185–216`。

脚本将注入文本放入当轮 API messages，但回写 history 时只保存用户问题和助手答案，注入内容在下一轮直接消失。实际本机 DSH `dsh-agent-loop@0.2.1-rc.4` 的 `step()` 会把 `decision.messages` 追加进 session。测试 agent 也没有实现 `inject()`，首轮短地图注入会失败后被插件捕获，因此这部分成本也未进入对照；没有真实 compaction/end 生命周期。

“按所写模拟协议算出 0.514”可以保留；“安装插件后 ≥10 轮可安全省 49%”超出证据。并且 D1 的事实预先直接入库，D2 只有 6/9 或 7/9 的弱命中，不能把两批的平均成本相减当作质量相同的真实净收益。

建议：下一轮使用相同用户输入、真实事件/持久历史/压缩边界，将抽取→写入→召回→回答连起来，计入工具 schema、短图、抽取、压缩与重试的全部 usage；质量不过关的臂不纳入“等质量省钱”结论。

### P2：0.8.1 的摘要规则没有统一到芯片与更正指纹

位置：`lib/pins.js:17–21,131`、`lib/context-budget.js:347`、`lib/store.js:418–423`。

同一长决策末尾的 `verify-QA-71.mjs`：recall 经过 preserveEnds 后可见；pin 在进入预算层前仍截前 200 字，且 pin 不再经过正文投影，末尾仍不可见。这是尾部保底覆盖遗漏。

另有本次新增联动缺陷：投递时 fingerprint 使用头尾摘要，`announceFactChange` 仍传前 200 字。对长事实**仅修改 aliases**（正文/期限都不变），pending corrections 从 0 变为 1，误报“内容或期限已更新”。发布说明中“同一规则贯穿”尚不完整。这项影响已发布的 0.8.1，但不等于需要撤回整包。

建议：让事实投影/变更身份有统一口径，保持历史 pin 不自动切到后继的原约束；增加长 pin、历史 pin、仅改别名、真正改正文/期限、重复更正的回归。

### P2：抽取质量证据不足以支持 7/9、6/9 作为准确率

位置：`scripts/bench-extract-cost.mjs:83`。

`found()` 在候选的 JSON 全文里找字符串；“3”会命中“30”，出现在 quote/name 也算，否定或不正确归属也可通过。记录没有保留完整候选和模型回答，发布包的精简器还删除 calls.response。费用 usage 可算，抽取语义却无法独立重判。

建议：像 C3 那样固定事实字段/主体/数值/极性/时效，保留原始输出和最终写入结果；错误事实、额外错误写入与漏记都计数。先离线用反例证明评分有效，再付费测闭环。

## 后续顺序与验收门槛

1. **R1：可靠性收口（零模型费用）。** 收窄/暂缓新门控；统一长摘要、pin 和更正指纹。上面反例先失败、修后通过，完整回归继续通过；禁止通过丢弃输入得到省钱数字。结束后评估是否发布 0.8.2，当前审查不发布。
2. **R2：修实验基础（零模型费用）。** 各臂独立库/会话、种植后数量与 hash 断言、失败预算守卫、调用级费用和评分修正；补齐原始候选/消息证据与只读清单校验。冻结协议前不再宣传 80%/等效/产品优越。
3. **R3：小规模真实宿主闭环。** 用少量覆盖中文事实/改口/长正文/并列/跨压缩的会话先试跑；再测 5/10/20 轮。同一次实验仍限 15 元，按最贵价格预留，未知费用或超预算立即停。先验证事实完整性，再比较全链路净费用；没有达标就交付失败样本，不追着调测试集。
4. **R4：规模优化另开小片。** 优先索引持久化有效性与批量 build，其次 keyword/锚点全扫。先用 1k/10k 证明开库与检索正确、p95 改善，再决定是否重跑 50k；保持 DIM=1536、默认开关、数据格式不变。

这四步不要求重写插件，也不需要现在引入新外部服务或扩大 UI。先让记录可靠、实验可信，再决定值得投入哪个性能方向。
