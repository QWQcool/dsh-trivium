## 3. 当前真正阻塞点

### A. 仍有可独立复现的整轮漏记

当前 `distillableTurns()` 会整轮排除含工具驱动措辞的用户消息。本次直接调用：

```text
输入：按顺序调用工具，生产端口是 9443。
shouldExtractBatch → { call: false, reason: "empty" }
```

这条消息同时包含事实，不能因为“按顺序调用工具”就全部消费掉。应分清纯操作语与事实片段；无法确认无事实时保留到原有抽取路径。回归必须验证最终库和pending状态，而非只检查正则。

### B. 真实宿主的长文本尾部仍漏记，根因尚未被报文证据定位

远端新增报告记录：R3第一片真实宿主采集预检16/16；第二片中姓名/端口/金额场景通过，改口场景需要语义复核，长正文尾部口令场景失败；第三片净成本实验未启动。

这不是本次重新执行的付费结果。报告明确承认S3缺少抽取请求级证据，不能确定是采集截断、抽取未触发、提示裁剪、候选过滤还是模型漏提取。当前代码确实存在用户消息500字符、助手400字符、工具200字符、抽取prompt2400字符等边界，但不能不看实际报文就把其中一处定为该样本根因。

### C. 证据采集与压缩仍有缺口

- R3报告中第一轮原始JSON被第二轮同名输出覆盖；控制台数字不能代替完整可复核证据。下一次试验前必须改成不可覆盖的run目录和调用级账本。
- 压缩后同一step重试缺短地图，下一step才恢复：要检查实际送给模型的上下文是否满足恢复契约，同时守住预算，不能仅看钩子是否触发。
- 纯空格变化的bodyKey误报优先级较低；先处理真实漏事实，不要以过度规范化破坏代码、数值或有语义的空白。

## 4. 下一轮分两条线

### 主线A：先补事实完整性，形成可靠性补丁候选

1. 开工时核对并同步远端证据提交，固定源码、内核、宿主和实验环境。依赖必须与锁文件一致，真实日常profile和数据库不用于故障测试。
2. 把“工具指令+中文事实”的混合句变成失败回归，修掉整轮过滤。覆盖姓名、端口、次数、否定、改口、助手与工具事实；无事实的纯操作句仍可跳过。
3. 给长文本链路加分阶段证据：用户事件→缓冲→抽取请求→原始响应→解析候选→过滤后候选→最终库→新会话召回。每段记录长度、合成事实位置与内容hash；关键事实因预算未处理时不得记成已消费。
4. 用头/中/尾、并列与跨消息fixture定位截断。优先考虑有界分段和可恢复pending，不把所有字符上限无限放大，也不只修最后的展示摘要。
5. 先用受控模型桩走真实宿主失败/重试/压缩，再按单独确定的模型与费用预算小样本重验真实质量。保留严格判分与人工语义复核，不把正确改写直接当漏记，也不把子串命中当准确。
6. 新事实完整性验收通过后再评估下一补丁版；净费用矩阵和50k规模重测后置。当前不宣传固定节省比例。

### 适配线E：可以先做零费用、只读的B站接线

不必等完整成本矩阵才设计生态协议。E0可与主线A穿插：用明确手工写入、已确认的合成偏好与预录候选，先证明消费者能收到正确范围、正确版本的记忆。

但不能把“手工种植fixture接通”当成“自然聊天自动记忆已可靠”。上线前仍须单独补用户表达→记住→新任务消费的全链路。

首个适配对象建议为 `c1overzz/dsh-bili-scroll`，详细任务见 [B站适配计划](BILI-ADAPTER-PLAN-2026-10-30.md)。暂不同时做SurfCore、AstrBot、多用户和双向同步。
