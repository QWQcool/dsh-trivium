# A-10：把两个已修场景拉大到 n=10

目的：A-6（改口退休）和 A-7（先重放再建图）当时都只有 n=5，`4/5`、`5/5` 说明不了稳定性。这轮把两个场景各跑到 10 次，同时把实验脚本的熔断标记改成**按任务**记录（A-9 只能记录整轮）。

| NEGATION（否定约束） | 10/10 | 10/10 | **10/10** | 10/10 | 0/19 | 3/10（全部在 setup） | ¥0.123926 |

两次合计 39 次抽取调用、零截断、**20/20 答对**。修前同一夹具 CORRECTION 是 3/5，中间态 4/5。

## 2. 熔断触发在哪：是 agent 在逛工作区，不是记忆在绕圈

NEGATION 有 **3/10** 轮在**第二个 setup 轮**（内容只有“继续。”）里超过 12 个请求，被熔断标记为 `request-cap`（39–63 秒），费用明显偏高（¥0.036 / ¥0.018 vs 中位数 ¥0.007）。

把这些轮次的报文逐条解开，**循环里调用的不是我们的记忆工具**：

```text
#1 -> [ctx_remember]          ← 记忆写入，一次
#4 -> [get_goal, pwsh]
#5 -> [ctx_find, pwsh]
#6 -> [pwsh]  #7 -> [pwsh]  #8 -> [pwsh, read]
#9 -> [pwsh, read]  ... #13 -> [grep, pwsh]  #14 -> [pwsh]
```

也就是说：模型把“继续。”理解成“去干活”，于是用 `pwsh`/`read`/`glob`/`grep` **翻我们真实仓库**。这是宿主里正常的 agent 行为，不是记忆插件的 bug——我最初把它归因成“反复 `ctx_find`”，逐条报文推翻了它。

真正要改的是**实验设计**：记忆测试的 setup 轮不该让 agent 有活可干。

- 熔断按任务归属（`aborted: [{step:'setup'|'question', reason, ms}]`），能直接看出是哪一步失控；
- `question` 步 **0/10** 触发 → 提问轮本身是稳的，浪费都发生在 setup；
- 这也解释了 A-5b 那次 43 请求：同样是 cwd 指向真实仓库后，agent 开始自己找活干。

## 5. 换空工作区复跑（验证上面的归因）

只改了实验条件：每轮在 `os.tmpdir()` 下新建**空目录**作为 cwd（提示词、判分、模型全部不动）。

| 场景 | cwd | 运行 | 答对 | 触发熔断 | 单次均值 |
|---|---|---|---|---|---|
| NEGATION | 仓库内 `ws` | 10 | 10/10 | **3** | ¥0.0124 |
| NEGATION | **空目录** | 5 | **5/5** | **0** | **¥0.0039** |
| CORRECTION | 仓库内 `ws` | 10 | 10/10 | 0 | ¥0.0077 |
| CORRECTION | **空目录** | 5 | **5/5** | 0 | ¥0.0085 |

- NEGATION 的**单次成本降到约 1/3**，方差消失（5 次全部落在 ¥0.0035–0.0045）；
- 两个场景质量不变（都是 5/5）；
- CORRECTION 本来就不逛仓库，换空目录后单次成本基本持平。

这直接证实了第 2 节的归因：**熔断和成本方差来自 agent 在工作区里找活干，不是记忆链路**。

追加费用：NEGATION ×5 ¥0.019626 + CORRECTION ×5 ¥0.042704 = **¥0.062330**。
