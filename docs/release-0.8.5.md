# 0.8.5 — 内核升级（只有内核）

2026-11-05。**这一版只做一件事：`triviumdb` 从 `0.9.0-beta.3` 升到 `0.9.0`。**

记忆管线的改动（事件快筛、地图热度、增量注入与新轮次键、事实身份、批量写入、新诊断、
`MemoryWriter`、scope / inherit / Router）**全部顺延到 0.8.6**，不在这个包里。

## 为什么只有内核

0.9.0 修了我们反复踩的两件事：关闭后重新打开拿到已删除句柄、Windows 上原子替换期间的锁路径竞态。
这些是已经在生产上出现过的问题，值得单独发。

而管线改动会改变"记忆里到底存了什么"，两者混在一个版本里，出问题时分不清是内核还是插件行为。
拆开之后，这个版本的验收范围就是：**同样的行为，跑在新的内核上**。

## 唯一必要的代码适配

0.9.0 的类型化存储**拒绝 `undefined`**（beta.3 静默丢弃）。我们的 payload 大量使用可选字段展开，
所以 `lib/store.js` 在引擎边界统一做一次 `pruneForStorage`，写面取自 `triviumdb.d.ts`：

```
insert / insertWithId / updatePayload / updateEdge / commitTransaction
```

除此之外**没有行为改动**：默认开关、召回、抽取、预算、去重、替代判据、四个模型工具的
名称/参数/返回全部不变。

## 升级前必须做：备份整个 `.dsh` 目录

> 0.9.0 把库文件版本升到 **v10**，旧内核读不了（`TDB_UNSUPPORTED_DATABASE_VERSION`）。
> 也就是说**降级插件不是回退**，恢复备份才是。

- 备份要复制**整个文件组**：`trivium.tdb` 以及同前缀的 `.gidx` `.pidx` `.pld.*` `.text` `.text.meta`
  `.vec` `.wal` `.lock` `.flush_ok`。只复制 `.tdb` 会得到 `TDB_CORRUPTED_FILE`。
- 备份时请关闭插件（避免读到写了一半的文件组）。

## 验证

| 项 | 结果 |
|---|---|
| 全量回归（0.8.4 基线那 74 个 smoke） | **74/74** |
| 历史库升级 + 重开 + 全量内容摘要比对 | 通过（`node scripts/verify-kernel-upgrade.mjs <含 trivium.tdb* 的目录> --expect-kernel=0.9.0`） |
| 恢复升级前备份，并由 `0.9.0-beta.3` 打开 | 通过（`--probe --expect-kernel=0.9.0-beta.3`） |
| 用旧内核打开 v10 库 | 按预期被拒绝（`TDB_UNSUPPORTED_DATABASE_VERSION`） |
| 打包 | `npm pack --dry-run` 通过，无本机路径泄漏 |

演练脚本会**断言实际加载的内核版本**，版本不符即判失败——这条是上一轮复审指出的问题，
现在写进了脚本本身。

## 已知限制

1. 演练只用了一个库（仓库工作区），没有跨机恢复，也没有 `0.8.11` 的降级测试。
2. `0.9.0` 的批量写入路径比 beta.3 慢（同一份基准 p95 206 → 483 ms）；本版本不涉及批量写入，
   但 0.8.6 会带着这条数据一起发布。
3. 升级到 v10 之后，**唯一**的回退方式是恢复备份；库里已有数据不会被改写，但格式不可逆。
